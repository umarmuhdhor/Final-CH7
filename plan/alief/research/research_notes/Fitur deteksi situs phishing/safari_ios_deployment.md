# Deploying phishing / scam detection in an iPhone Safari Web Extension (MV3) plus a server layer: platform limits and real-world evidence from deployed detectors

Scope note: research done 26 Oct 2026 for Shoo (iOS Safari Web Extension, MV3, plus a Cloudflare Workers server). Shoo today: `background.scripts` + `"persistent": false` + `"type": "module"`, content scripts on `<all_urls>` at `document_idle`, `host_permissions: ["<all_urls>"]`, `permissions: ["nativeMessaging","storage","alarms"]`. Every network call already goes through `background.js` (repo: `ios/ShooExtension/Resources/manifest.json`, `ios/ShooExtension/CLAUDE.md`). This file does not repeat the feature-effectiveness work in `url_domain_tls.md`, `html_headers_redirect.md` and `visual_llm.md`. It resolves the Safari questions those notes left open. MDN browser-compat-data (BCD) values below come from the raw JSON on GitHub `main`, read 26 Oct 2026. Apple doc text comes from the developer.apple.com markdown endpoints, read the same day. Developer-forum and Bugzilla items are marked **[non-authoritative]**. Items older than 2022 are marked **[older]**.

## Q1. What can an iOS Safari Web Extension technically do for detection, and since which iOS/Safari version?

### Takeaway
Content scripts (full DOM, all frames, MAIN world), `webNavigation` (basic events only), `declarativeNetRequest` (block/redirect, dynamic rules), `scripting`, `captureVisibleTab`, `storage` and background `fetch` all work on iOS. Most have worked since iOS 15–16.4. The big exception is `webRequest`. BCD says iOS 18, but Apple's own compatibility page says plainly "`webRequest`: Not supported in iOS." Plan as if Shoo cannot see HTTP headers or 3xx redirect hops on iPhone until a device test proves otherwise. The background context is non-persistent and gets unloaded. iOS 17.4–18.6 had documented kill bugs, mostly hitting `service_worker` backgrounds. Shoo's `scripts` + `persistent:false` setup is the forum-reported workaround.

### Cited Findings

**Background page / service worker lifetime**
- Apple: "In iOS, you must make your background page nonpersistent. Safari unloads your nonpersistent background page when the user isn't directly interacting with the extension". Apple says to add listeners at top level, keep state in `storage`, and use `alarms` instead of `setTimeout`. Apple also says to keep the background persistent **on macOS** if you use `webRequest`, "due to the frequency of callbacks that might fail if Safari unloads the background page." — [Apple Developer, "Optimizing your web extension for Safari"](https://developer.apple.com/documentation/safariservices/optimizing-your-web-extension-for-safari)
- Apple compatibility page: "`background`: In iOS, you need to set the `persistent` attribute to `false`. With manifest version 3, all background pages are nonpersistent." — [Apple Developer, "Assessing your Safari web extension's browser compatibility"](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)
- BCD: `background.persistent` on iOS is partial from 15 and supports only non-persistent pages. `background.service_worker` iOS 15.4. `background.type` (module) iOS 16.4. `background.preferred_environment` iOS 18. — [MDN BCD, webextensions/manifest/background.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/background.json)
- No official lifetime or memory number for the background page was found. **[non-authoritative]** Forum thread 758346 (Jun 2024–Sep 2025) reports that on iOS 17.4.x–17.6 the service worker was "permanently killed" about 30–45 s after install. After the kill, no `webNavigation` event woke it, and `runtime.sendMessage` from content scripts "returns undefined to the content script immediately." Only a reboot or toggling the extension restored it. The 17.6 beta notes say "Fixed an issue where Safari Web Extension background pages would stop responding after about 30 seconds. (127681420)". An Apple engineer said it was fixed in 17.6.1. Developers reported it still unfixed in 18 and in 18.6.2 (Aug 2025). The workaround is `"scripts": [...], "persistent": false` instead of `service_worker`: the page "is still unloaded but correctly starts up again when needed." — [Apple Developer Forums 758346](https://developer.apple.com/forums/thread/758346); [thread 721222](https://developer.apple.com/forums/thread/721222)
- **[non-authoritative]** One developer estimated that iOS kills the worker at about 80% RAM use, especially on low-RAM iPads. — [Apple Developer Forums 721222](https://developer.apple.com/forums/thread/721222). On iOS 17.5 the background script stalled after rapid messages (1–4 s apart). Apple said the fix shipped in 17.6/18 betas. A later reply said listeners still died after a device lock. — [Apple Developer Forums 757926](https://developer.apple.com/forums/thread/757926)

**Content scripts**
- BCD `content_scripts`: iOS 15, with the note "Content scripts are not applied to tabs until the user grants permission via the extension's access alert. Additional loads after permission is granted will respect `run_at`." `all_frames` iOS 15. `exclude_matches` 15. `match_about_blank` and `match_origin_as_fallback` iOS 18.4. `world` (MAIN/ISOLATED) iOS 18. `include_globs`/`exclude_globs` not supported. `css_origin` 18. — [MDN BCD, webextensions/manifest/content_scripts.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/content_scripts.json)
- Apple permission model: if a site has no grant, Safari shows a badge. "In iOS, the user selects the extension's entry in the More menu, and selects a permission option." Users manage Ask/Allow/Deny per site in Settings > Safari > Extensions. Apple tells developers to "Prioritize using `activeTab`, host permissions, and `optional_permissions`; only use `<all_urls>` if there is no other option." In Safari 17+, a per-site grant applies across all profiles and Private Browsing. — [Apple Developer, "Managing Safari web extension permissions"](https://developer.apple.com/documentation/safariservices/managing-safari-web-extension-permissions)
- BCD `permissions.request` iOS 15 note: requesting `<all_urls>` or `*://*/*` grants permission to request specific origins and "automatically prompt the user for access to any visited website via the extension's banner." `host_permissions` iOS 15.4. `optional_host_permissions` iOS 15.5. — [MDN BCD, webextensions/api/permissions.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/permissions.json); [manifest/host_permissions.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/host_permissions.json)
- Repo finding, 26 Oct 2026, commit 9a1feb9: Safari's "Allow on every website" grants `*://*/*`, and WebKit does not count it as covering `<all_urls>`. So `permissions.contains({origins:["<all_urls>"]})` returned false even with full access. — [Shoo repo, ios/ShooExtension/Resources/heartbeat.js]
- Safari 26.0 added `dom.openOrClosedShadowRoot()` for web extensions, which lets content scripts read closed shadow DOM. — [WebKit, "WebKit Features in Safari 26.0" (2025)](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)

**scripting / tabs**
- BCD `scripting.executeScript` iOS 15.4. `world: MAIN` 15.4. `InjectionResult` 17 (`.error` 17.4, `.documentId` 18.4). `injectImmediately` is partial: "Scripts are always injected immediately." `registerContentScripts`/`unregisterContentScripts` 16.4. `RegisteredContentScript.world` 16.4. `tabs.executeScript` is MV2 only. — [MDN BCD, webextensions/api/scripting.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/scripting.json); [tabs.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/tabs.json)
- Apple: `scripting.executeScript`: "`injectImmediately` not supported". `scripting.insertCSS`/`removeCSS`: "`origin`, `allFrames`, `frameIds` not supported". Note: `html_headers_redirect.md` attributed the `allFrames`/`frameIds` limit to `executeScript`. On Apple's page it applies to `insertCSS`/`removeCSS`. — [Apple, "Assessing… compatibility"](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)
- BCD `tabs.captureVisibleTab` iOS 15, notes "default file format is 'jpeg'" and "`<all_urls>` permission is optional". Apple: "`tabs.captureVisibleTab`: Doesn't require `all_urls` permission." Apple also says `tabs` needs host permission. — [MDN BCD tabs.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/tabs.json); [Apple, "Assessing… compatibility"](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)

**webNavigation**
- BCD: `onBeforeNavigate`, `onCommitted`, `onDOMContentLoaded`, `onCompleted`, `onErrorOccurred`, `getFrame`, `getAllFrames` all iOS 15. `documentId`/`parentDocumentId` 18.4. **Not supported:** `onHistoryStateUpdated` (no SPA pushState events), `onReferenceFragmentUpdated`, `onCreatedNavigationTarget`, `onTabReplaced`, `transitionType`, `transitionQualifiers`, `frameType`, `documentLifecycle`, `parentFrameId` on onCommitted/onCompleted. — [MDN BCD, webextensions/api/webNavigation.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/webNavigation.json)
- Apple agrees: "`webNavigation`: `onCreatedNavigationTarget`, `onReferenceFragmentUpdated`, `onTabReplaced`, `onHistoryStateUpdated` not supported. `transitionType`, `transitionQualifiers` not supported." — [Apple, "Assessing… compatibility"](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)

**webRequest (the MDN vs Apple conflict)**
- BCD: `webRequest` safari_ios "18". macOS 14–17 note: "Only worked with Manifest V2 extensions using persistent background content." No blocking. — [MDN BCD webRequest.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/webRequest.json)
- Apple, current page: "`webRequest`: Not supported in iOS. `BlockingResponse` not supported. Blocking requests not supported. `opt_extraInfoSpec` not supported for any of the events." Also: "`permissions.webRequestBlocking`: Not supported. Use `permissions.webRequest` instead for macOS only." — [Apple, "Assessing… compatibility"](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)
- Safari 18.4 notes include webRequest fixes ("Fixed webRequest event listeners to honor extraInfoSpec", "`onBeforeRequest` event missing the `requestBody`") and `documentId` in webRequest. They do not say iOS gained webRequest. Safari 26.0 notes: "Fixed a non-fatal webRequest error for non-persistent background content. (150051544)". — [WebKit, "WebKit Features in Safari 18.4" (2025)](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/); [WebKit, Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- **[non-authoritative]** On macOS 15.4 / Safari 18.4, a developer saw a Settings error about non-persistent background content and webRequest, but `onHeadersReceived` still fired. — [Apple Developer Forums 781636](https://developer.apple.com/forums/thread/781636)

**declarativeNetRequest (DNR)**
- BCD: `declarativeNetRequest` iOS 15. `Redirect` 15.4. `updateDynamicRules`/`updateSessionRules`/`getMatchedRules` 15.4. `isRegexSupported` 15. `MAX_NUMBER_OF_STATIC_RULESETS` 15. `MAX_NUMBER_OF_ENABLED_STATIC_RULESETS` and `MAX_NUMBER_OF_DYNAMIC_AND_SESSION_RULES` 16.4. `RuleCondition.requestDomains`/`excludedRequestDomains` 16.4. `initiatorDomains` iOS 26. `RuleAction.requestHeaders` 16.4. `responseHeaders` not supported. **`onRuleMatchedDebug` not supported.** `MAX_NUMBER_OF_DYNAMIC_RULES`, `MAX_NUMBER_OF_REGEX_RULES`, `GUARANTEED_MINIMUM_STATIC_RULES` constants not exposed. Resource types `main_frame`, `sub_frame`, `xmlhttprequest`, `websocket`, `ping` supported. — [MDN BCD declarativeNetRequest.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/declarativeNetRequest.json)
- Safari 18.4: "Fixed a slowdown in applying rulesets and dynamic rules in declarativeNetRequest. (136394861)". Safari 26.0 fixed high-priority redirects not overriding low-priority blocks (145241581). It also fixed "a declarativeNetRequest bug that prevents redirects to extension resources (145569361)", fixed higher numbers being treated as higher priority (145570245), and fixed `allowAllRequests` priority (152746422). — [WebKit 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/); [WebKit 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- Rule-count values (50 static rulesets, 10 enabled) and `declarativeNetRequestWithHostAccess` for redirects are already in `html_headers_redirect.md` (WWDC22 10099, WWDC26 216).

### Inferences
- Feasibility matrix for Shoo. "Prompt impact" is relative to today's manifest, which already has `<all_urls>` host permission, so most rows add no new website-access prompt.

| Capability | iOS status (min version) | Where it runs | Privacy cost | Prompt / permission impact |
|---|---|---|---|---|
| Full DOM read, forms, text, `MutationObserver` for late forms | Feasible, iOS 15 | Content script | Low if kept on device | None new (already `<all_urls>`). Not active until the user grants site access |
| Cross-origin iframes (e.g. embedded login frames) | Feasible via `all_frames: true`, iOS 15. `about:blank`/srcdoc frames need `match_about_blank` / `match_origin_as_fallback`, iOS 18.4 | Content script per frame (own origin) | Low | None new. Each frame's origin must be granted |
| `document_start` injection (catch scripts before page JS) | Feasible, iOS 15. The first load after a new grant may not respect `run_at` (BCD note) | Content script | Low | None |
| MAIN-world hooks (wrap `fetch`/XHR, see exfil targets) | Feasible: `content_scripts.world` iOS 18, `scripting.executeScript({world:'MAIN'})` iOS 15.4 | Page world | Medium: sees page traffic. Keep only derived flags | None new, but App Review / privacy label scrutiny |
| SPA URL changes | `webNavigation.onHistoryStateUpdated` not supported. Use content-script `popstate`/URL polling | Content script | Low | None |
| Navigation events (before/committed/completed, errors) | Feasible, iOS 15. No `transitionType` (cannot tell "typed" vs "link") | Background | Low | Needs `webNavigation` permission added |
| HTTP response headers, 3xx hops | **Treat as not possible on iOS** (Apple: "Not supported in iOS"). BCD says 18. Device test required | — | — | Would need `webRequest` permission |
| Same-origin redirect count, Server-Timing of the page | Feasible: `redirectCount` iOS 15.1, `serverTiming` 16.4. Cross-origin hops read as 0 | Content script | Low | None |
| `document.referrer` (e.g. came from WhatsApp/SMS deep link vs search) | Feasible (iOS 1), but Referrer-Policy often trims it to the origin or empties it | Content script | Low | None |
| Pre-load block / redirect to warning page | Feasible: DNR iOS 15, Redirect + dynamic rules 15.4. Redirect to extension page fixed in Safari 26 | Browser engine | Very low (no URL leaves device) | `declarativeNetRequest` (+ `…WithHostAccess` for redirect) |
| Know which DNR rule fired | `getMatchedRules` iOS 15.4 only (no `onRuleMatchedDebug`) | Background | Low | — |
| Screenshot for visual check | Feasible: `captureVisibleTab` iOS 15, JPEG default | Background | High if uploaded. OK if processed on device | None (Apple: no `all_urls` needed) |
| Cross-origin `fetch` (RDAP, CT, own Worker) | Feasible from background. Safari 18.4+ needs a `permissions.request({origins: []})` call first for CORS-blocked fetch | Background | Each fetch reveals the queried domain to that server | Host permission for target |
| Local blocklist / model storage | `storage.local` 5 MB, unlimited with `unlimitedStorage` (Safari 16+). `storage.session` 16.4 | Background | None | `unlimitedStorage` permission |
- Because the background can be unloaded at any time, and on some iOS builds killed for good, detection that must always run should live in the content script (synchronous, page-lifetime). The background should be treated as a best-effort relay. Shoo's layer 1–2 already sits in content scripts (`detector.js`), which matches this.
- On iOS, the extension cannot reconstruct redirect chains or read headers. The only redirect signals available are `webNavigation` URL sequences (onBeforeNavigate → onCommitted in the same tab) and same-origin `redirectCount`. Server-side, the Worker can re-fetch the registrable domain's root and follow redirects itself (already flagged as [S-domain] in earlier notes).

### Gaps
- Whether `browser.webRequest` exists at all in an iOS 18.4+/26 Safari extension. Apple says no. BCD says yes. Needs a `typeof browser.webRequest` check plus an `onHeadersReceived` listener test on a real iPhone.
- No official number for background-page memory or idle-unload timeout on iOS. Forum reports only.
- Exact DNR numeric limits on iOS (dynamic rules, regex rules). BCD marks the constants unsupported, so read the values with `getAvailableStaticRuleCount` / try-insert on device.
- Whether `performance.getEntriesByType('navigation')` in an ISOLATED-world Safari content script returns the page's entry (expected, since `performance` is a window API, but not documented for Safari content scripts).
- Whether `captureVisibleTab` works from a non-persistent background on iOS without a user gesture. Not documented.

## Q2. Native messaging and the native extension handler: latency, size, App Group, network and on-device ML within memory limits

### Takeaway
Only the background page or extension pages can call `browser.runtime.sendNativeMessage`, and the message goes to the extension's own `SafariWebExtensionHandler` (an app extension process), not to the app. Content scripts cannot use it. On iOS the containing app cannot push messages to the JS side. Data is shared through an App Group. The handler process had a 6 MB memory cap on iOS 15.0, raised to 80 MB in iOS 15.1 per an Apple engineer. There is no newer official number. Apple publishes no latency or size limits. So the native side suits small, fast jobs (App Group reads/writes, a small Core ML / NaturalLanguage model). It does not suit big models or long network work.

### Cited Findings
- Apple: a Safari web extension has three sandboxed parts: the app, the JS, and "a native app extension that mediates between the macOS or iOS app and the JavaScript code." "Content scripts that are injected into web content cannot send messages to the native app extension." Messages need the `nativeMessaging` permission. "Safari ignores the `application.id` parameter and only sends the message to the containing app's native app extension." The handler implements `beginRequest(with:)`, reads `SFExtensionMessageKey`, gets `SFExtensionProfileKey` in Safari 17+, and replies via `completeRequest`. The app and the native extension "cannot share data in their respective containers" except through App Groups. "You can't send messages from a containing iOS app to your web extension's JavaScript scripts." `connectNative` + `SFSafariApplication.dispatchMessage` is described for **macOS** apps only. — [Apple Developer, "Messaging between the app and JavaScript in a Safari web extension"](https://developer.apple.com/documentation/safariservices/messaging-between-the-app-and-javascript-in-a-safari-web-extension)
- BCD lists `runtime.sendNativeMessage` and `runtime.connectNative` as iOS 15, pointing to the Apple doc above for details. — [MDN BCD runtime.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/runtime.json)
- Memory: in Aug–Sep 2021 developers reported "The limit for Safari Extensions is explicitly set to 6MB". An Apple Frameworks Engineer replied (Oct 2021): "The limit increased to 80MB in the latest iOS 15.1 beta," and "This change will not go back into 15.0." **[older, non-authoritative forum but Apple-staff reply]** — [Apple Developer Forums 687642](https://developer.apple.com/forums/thread/687642)
- **[non-authoritative]** Reliability reports. Handler requests went unanswered on physical devices but worked when Xcode/Console was attached ([thread 693959](https://developer.apple.com/forums/thread/693959)). Completion handlers never ran when the `nativeMessaging` permission was missing ([651164](https://developer.apple.com/forums/thread/651164)). `sendNativeMessage` failed with error 4099 "Couldn't communicate with a helper application" ([747067](https://developer.apple.com/forums/thread/747067)).
- Apple ML research: an ANE-optimized DistilBERT runs "up to 10 times faster" with "14 times less memory" than the baseline Core ML deployment. The reference code targets A14+/M1+, with figures for iPhone 13 on iOS 16. — [Apple Machine Learning Research, "Deploying Transformers on the Apple Neural Engine" (2022)](https://machinelearning.apple.com/research/neural-engine-transformers) **[older]**; [apple/ml-ane-transformers README](https://github.com/apple/ml-ane-transformers)

### Inferences
- Shoo's existing pattern (content script → `runtime.sendMessage` → background → `sendNativeMessage` → handler → App Group) is the only supported path. Every native call costs two IPC hops plus a possible cold start of the handler process. Keep it off the critical path of the "block before the user types" decision.
- An 80 MB cap (if still current) leaves room for a small NaturalLanguage/Create ML text classifier or a quantized DistilBERT-class Core ML model (tens of MB). It does not leave room for an LLM. Load the model lazily and expect jetsam kills under memory pressure. Apple's 10x/14x numbers suggest ANE inference of a DistilBERT-class model is fast, but no Safari-extension measurement exists.
- `URLSession` from the handler is technically an app-extension capability. Routing network calls through native code mainly helps when the server must not see a `safari-web-extension://` origin, or when using Apple frameworks (e.g. future PIR). Otherwise the background `fetch` is simpler.

### Gaps
- No Apple doc states the current (iOS 17–26) memory limit for the Safari web extension handler. No measured `sendNativeMessage` round-trip latency or maximum message size was found. Measure on device (e.g. 1 KB vs 100 KB vs 1 MB payloads).
- Did not fetch Apple's App Extension Programming Guide text on `URLSession` in extensions or on per-extension memory, so there is no citation for network-call rules in the handler.
- Whether Core ML / Vision / NaturalLanguage run reliably inside the Safari extension handler under the cap: no report found.

## Q3. On-device ML inside the Safari extension JS context (WASM, WebGPU, ONNX Runtime Web, TF.js, Transformers.js)

### Takeaway
The building blocks exist on iOS 26: WebGPU ships, and `'wasm-unsafe-eval'` is parsed correctly in extension CSP since Safari 26. But no source documents ONNX Runtime Web, TF.js or Transformers.js inside an **iOS Safari extension**. WebKit bugs show unstable WASM memory on iPhone. The only measured client-side transformer detector (PhishLang, MobileBERT) runs as a local server process on desktop, at 0.4–0.8 s per page and 76–102 MB median RAM. Too heavy for an iOS extension background that may be unloaded.

### Cited Findings
- WebGPU "is now shipping in Safari 26.0 for macOS, iOS, iPadOS, and visionOS". BCD `api.GPU` iOS 26. Safari 26 also made WebAssembly first run in a new in-place interpreter, so large modules "launch even faster and use less memory." — [WebKit, Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/); [MDN BCD api/GPU.json](https://github.com/mdn/browser-compat-data/blob/main/api/GPU.json)
- Safari 26 fixed "wasm-unsafe-eval to not get parsed as a valid CSP keyword (147551225)". Before 26, WASM in extension pages under an MV3 CSP may have been blocked. — [WebKit 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- WebKit WASM memory instability on iPhone (bugs 269777, 221530) is already cited in `visual_llm.md` §6.
- ONNX Runtime Web's compatibility table lists Safari (macOS) with wasm and webgl, and has no iOS column. — [ONNX Runtime Web README (npm 1.19.0)](https://cdn.jsdelivr.net/npm/onnxruntime-web@1.19.0/README.md). Chrome MV3 extensions need the ONNX/WASM files bundled locally and `'wasm-unsafe-eval'` in the CSP. **[non-authoritative]** — [Medium, "Running Transformers.js inside a Chrome extension (MV3)"](https://medium.com/@vprprudhvi/running-transformers-js-inside-a-chrome-extension-manifest-v3-a-practical-patch-d7ce4d6a0eac)
- PhishLang (Roy & Nilizadeh, NDSS 2026; arXiv 2408.05667). MobileBERT, 25M params, 74 MB inference memory. Median inference without page fetch: 0.44 s (Xeon), 0.59 s (i5-13th gen, 8 GB), 0.73 s (Celeron N4500, 2 GB), 0.81 s (2-core VM). Extension median memory 76–102 MB (28–247 MB peak). Accuracy 0.96, F1 0.96. 5/1,000 parked pages flagged. The model runs as "a local server" that the Chromium extension calls. Supports Windows/Linux only, and iOS/mobile is not supported. Field run: 42.7M domains (Sep 2023–Jan 2024), 25,796 flagged (0.057%). — [arXiv 2408.05667v3](https://arxiv.org/html/2408.05667v3); [NDSS 2026 paper page](https://www.ndss-symposium.org/ndss-paper/phishlang-a-real-time-fully-client-side-phishing-detection-framework-using-mobilebert)
- Chrome's deployed image-based phishing classifier (color-histogram "pixel loop") ran in 1.8 s on average before M92 and ~100 ms after, "up to 50 times faster at the 50th percentile and 2.5 times faster at the 99th percentile". Requests over 5 s fell from 16.25% to under 1.6%. Google: "Less CPU time means less battery drain." — [Chromium Blog, "Faster and more efficient phishing detection in M92" (Jul 2021)](https://blog.chromium.org/2021/07/m92-faster-and-more-efficient-phishing-detection.html) **[older]**

### Inferences
- Realistic on-device ML for Shoo today: (a) a tiny hand-built or logistic/GBDT model in plain JS over lexical URL + DOM features (KB-sized, sub-ms), and (b) a native Core ML/NaturalLanguage text classifier behind `sendNativeMessage`, if the 80 MB cap holds. Transformer/WASM/WebGPU inference in the extension JS is an R&D spike for iOS 26+ only, not a v1 feature.
- Chrome's own history is a useful budget: even Google's tuned classifier took 1.8 s per page until 2021. Its feature extractor has a hard 500 ms timeout (see Q4). A Shoo on-device layer should stay well under ~100 ms on a mid-range iPhone, or run after first paint without blocking.

### Gaps
- No measured inference latency or battery for any phishing model running inside an iOS Safari extension (JS or native handler). No report of ONNX Runtime Web / TF.js / Transformers.js working in an iOS Safari extension context.
- No data on WebGPU availability inside extension background pages (vs normal pages) on iOS 26.

## Q4. How deployed client-side and hybrid detectors perform in practice (Safe Browsing, Safari, SmartScreen/Edge, Chrome CSD, academic tools, warning studies)

### Takeaway
Big deployed systems are all hybrids. A local hash list or cheap model runs first, and the server decides. Blocklists alone are slow (minutes to hours, and mobile is slower), so vendors moved to real-time server checks. Chrome's on-device content classifier performed poorly in an independent study (14% detection on classified pages, 34% never classified, 500 ms timeout exploitable). Warning effectiveness depends on design and context. Active, interruptive warnings are heeded far more than passive ones. Click-through runs about 10–25% for phishing/malware interstitials, and link-focused, forced-attention warnings do best.

### Cited Findings

**Google Safe Browsing (GSB) and Chrome**
- Chrome Standard protection (Mar 2024) moved from a local list "updated every 30 to 60 minutes" to real-time server checks because "the average malicious site actually exists for less than 10 minutes". Google expects to "block 25% more phishing attempts" (a projection, not a measurement). GSB covers >5B devices, >10B URLs/files assessed daily, >3M warnings daily. It rolled out on desktop and iOS first. — [Google Keyword blog, "Google Safe Browsing protection in Chrome goes real-time" (14 Mar 2024)](https://blog.google/products/chrome/google-chrome-safe-browsing-real-time/)
- Privacy design of that change: hash prefixes are sent through an Oblivious HTTP relay operated by Fastly. "Safe Browsing sees the hash prefixes of your URL but not your IP address, and the privacy server sees your IP address but not the hash prefixes." — [The Hacker News, "Google introduces enhanced real-time…" (Mar 2024)](https://thehackernews.com/2024/03/google-introduces-enhanced-real-time.html) (secondary, quoting Google)
- Chrome client-side detection (CSD), independent study (Pourmohamad, Wirsz, Oest, Bao, Shoshitaishvili, Wang, Doupé, Bazzi). Code analysis of Chromium 79–108 plus PhishFarm experiments with 735 sites. Chrome downloads a content-based model (URL, DOM, term features) and a visual model with thresholds from GSB. In May 2020 only 66% of 300 phishing sites were even classified, and "just 14%" of those were detected. 34% bypassed classification (model-load failure 37%, reload issues 22%, DOM-extraction failure 11%). Feature extraction has a 500 ms limit, and exceeding it aborts classification (exploitable by DOM padding). It was ineffective against cloaking and against non-login phishing. On a flag, Chrome sends the URL plus ~21 attributes to GSB, which raises a privacy concern after false positives. Blocklisting (Apr 2023): none blocked within 30 min, ~10% within 1 h, ~51% after 7 days. Median 88 min desktop vs 3 h mobile (May 2020). — [Pourmohamad et al., "Deep Dive into Client-Side Anti-Phishing: A Longitudinal Study Bridging Academia and Industry", ACM AsiaCCS 2024](https://adamdoupe.com/publications/client-side-anti-phishing-asiaccs2024.pdf)
- Chrome 137 (May 2025) added Gemini Nano (on-device LLM) for Enhanced Protection users on desktop. It is invoked only when trigger behaviors appear (e.g. the Keyboard Lock API, typical of tech-support scams). It extracts signals such as page intent and sends them to Safe Browsing for the final verdict. Android was planned. — [BleepingComputer, "Google Chrome to use on-device AI to detect tech support scams" (May 2025)](https://www.bleepingcomputer.com/news/security/google-chrome-to-use-on-device-ai-to-detect-tech-support-scams/); [Infosecurity Magazine (May 2025)](https://www.infosecurity-magazine.com/news/google-ai-gemini-nano-scams-chrome/) (secondary)

**Apple Safari "Fraudulent Website Warning"**
- Safari checks a hash prefix of the URL against a local list. On a match it fetches the full hashes for that prefix and checks locally, so "the actual website address is never shared" with the provider. The list comes from Google, or from Tencent for devices with the mainland-China region code (Apple statement, Oct 2019). Providers "may also log your IP address". **[older]** — [The Register, "Apple China Tencent" (Oct 2019)](https://www.theregister.com/2019/10/14/apple_china_tencent); [MacTrast, Apple statement (Oct 2019)](https://www.mactrast.com/2019/10/apple-says-no-url-data-is-shared-with-chinese-company-tencent-and-tencent-checks-are-limited-to-mainland-china/)
- Since iOS 14.5, Safari proxies Safe Browsing requests through Apple (`proxy.safebrowsing.apple`) so Google does not see user IPs. Apple WebKit's lead said this was to "limit the risk of information leak." **[older]** — [9to5Mac (Feb 2021)](https://9to5mac.com/2021/02/11/fraudulent-website-warning/); [The Hacker News (Feb 2021)](https://thehackernews.com/2021/02/apple-will-proxy-safe-browsing-requests.html)
- Safari 26.0 added "a new configuration to support Google Safe Browsing version 5 traffic to Safari and WebKit clients with the web browser entitlement." — [WebKit, Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)

**Microsoft Edge / SmartScreen**
- Edge Scareware Blocker: "Edge runs a local machine learning model that detects suspicious full screen behaviors". Pages are checked "locally on your device by default", and no screenshots are sent unless the user adds one to feedback. On detection Edge exits full screen, mutes audio and warns. It can notify Defender SmartScreen "without sharing screenshots or any extra data beyond what SmartScreen already receives" (toggle: "Share detected scam sites with Microsoft Defender SmartScreen"). — [Microsoft, "Scareware blocker" feature page](https://www.microsoft.com/en-us/edge/features/scareware-blocker). No independent accuracy numbers found.

**Academic client-side extension detectors**
- PhishLang (see Q3): fully client-side MobileBERT. Its reports helped take down 74% of reported threats. GSB's detection of its JS-evasion samples rose from 35% to 73% after reporting. — [arXiv 2408.05667v3](https://arxiv.org/html/2408.05667v3)

**Warning effectiveness and false-positive cost**
- Akhawe & Porter Felt: >25M warning impressions (Chrome + Firefox telemetry). Click-through on malware/phishing warnings was ~10% in Firefox and ~25% in Chrome. SSL warnings: ~33% Firefox vs 70.2% Chrome. **[older]** — [Akhawe & Felt, "Alice in Warningland", USENIX Security 2013](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe)
- Egelman, Cranor & Hong: 60 participants in a lab spear-phishing study, 97% fell for at least one phish. With **active** (interruptive) warnings, 79% heeded them. The **passive** IE warning was heeded by only one participant per the abstract. A secondary summary says 13%, so check the paper before quoting. **[older]** — [Egelman et al., "You've Been Warned", CHI 2008, doi:10.1145/1357054.1357219](https://css.csail.mit.edu/6.566/2018/readings/youve-been-warned.pdf)
- Almuhimedi, Felt, Reeder, Consolvo: Chrome users click through about a fifth of malware warnings. They "consistently heed warnings about websites that they have not visited before" but respond unpredictably on previously visited sites. **[older]** — [SOUPS 2014, "Your Reputation Precedes You"](https://www.usenix.org/conference/soups2014/proceedings/presentation/almuhimedi)
- Reeder, Felt, Consolvo, Malkin, Thompson, Egelman: experience sampling with >6,000 Chrome/Firefox users on real warnings. Reasons for adhering or not "are many and vary with context". They found no single dominant failure such as habituation. Further gains need fixing "a range of smaller contextual misunderstandings." — [CHI 2018, "An Experience Sampling Study of User Reactions to Browser Warnings in the Field"](https://blues.cs.berkeley.edu/wp-content/uploads/2018/01/chi18-warnings.pdf)
- Petelka, Zou & Schaub (701 participants): link-focused warnings (next to the link, on hover, or forced attention where the original link is disabled) cut click-through compared with banner warnings. Forced attention was most effective. A 2025 follow-up found both focused attention and a time delay reduce click-through, and combining them reduces it more. — [Petelka et al., "Put Your Warning Where Your Link Is", CHI 2019, doi:10.1145/3290605.3300748](https://unpaywall.org/10.1145%2F3290605.3300748); [Petelka et al., SOUPS 2025 poster](https://www.usenix.org/conference/soups2025/presentation/petelka-poster)

### Inferences
- The industry pattern fits Shoo's plan: a cheap local check on every page, the server only on a local hit or uncertainty, and the final say on the server. Chrome's CSD failure modes are concrete design rules for Shoo's content script: model-load failure, a 500 ms timeout that DOM padding can trigger, and dependence on login forms. Do not abort silently on timeout. Cap the DOM walk and fall back to a partial verdict, and do not require a password field to score a page.
- Mobile blocklisting is slower (median 3 h vs 88 min in 2020). This argues for Shoo's on-device layer 2 and server layer 3 to cover the first hours, when Safari's own Fraudulent Website Warning is still silent.
- Warning design matters as much as the detector. Use an interruptive full-page block (`blocked.html`) only for high-confidence verdicts. Warnings on sites the user has visited before are ignored more, so do not escalate on returning, previously-allowed domains without strong evidence.

### Gaps
- No published false-positive rate in the wild for Safari's Fraudulent Website Warning, Edge Scareware Blocker or Chrome Gemini Nano. No public Netcraft extension evaluation found in this pass (not searched in depth).
- No mobile-specific (iPhone) warning click-through study after 2019 found.
- Original Google Security Blog post on Gemini Nano not fetched. Details rely on secondary press.

## Q5. Privacy-preserving lookup designs (hash prefix, k-anonymity, OHTTP, PIR) and whether to send only the registrable domain

### Takeaway
GSB v5 is the reference design. The client keeps a Global Cache of likely-benign hashes plus 4-byte-prefix threat lists, builds up to 30 host-suffix/path-prefix expressions, and sends only 4-byte SHA-256 prefixes (at most 30 per request, optionally padded with random prefixes) through an optional OHTTP relay. Apple has shipped a stronger option, homomorphic-encryption PIR (Live Caller ID Lookup, iOS 18), with open-source Swift tooling. For Shoo, hash-prefixing the registrable domain plus host suffixes gives roughly the same blocklist power as GSB's host checks without sending the domain in the clear. Cloudflare's own OHTTP relay is Enterprise-only and in closed beta, and its gateway refuses traffic from Workers.

### Cited Findings
- GSB v5 Real-Time mode: the client keeps "(i) a Global Cache of likely-benign sites, formatted as SHA256 hashes of host-suffix/path-prefix URL expressions, (ii) a set of threat lists, formatted as SHA256 hash prefixes". It checks the Global Cache first. A hit means UNSURE and falls back to local lists, so there is no network call. On a miss it sends 4-byte prefixes via `hashes.search` and caches full hashes with expiry. "It is also acceptable for the client to send unrelated or randomly generated hash prefixes together with" the real ones. — [Google, Safe Browsing v5 "Real-Time Mode"](https://developers.google.com/safe-browsing/reference/Real.Time.Mode)
- No-Storage mode: no persistent DB, only an in-memory cache, and every check goes to the server. At most 30 prefixes per request. A network error returns SAFE. — [Google, "No Storage Real-Time Mode"](https://developers.google.com/safe-browsing/reference/No.Storage.Real.Time.Mode)
- Canonicalization: "up to 30 different possible host suffix and path prefix combinations". Hosts try "at most five different strings", up to four starting from eTLD+1 (Public Suffix List) plus the full host. For `hashes.search`, "we currently require the hashes in the request to be truncated to exactly 4 bytes. Sending additional bytes in this request will compromise user privacy." — [Google, "URLs and Hashing"](https://developers.google.com/safe-browsing/reference/URLs.and.Hashing)
- Lists: `gc-32b` (Global Cache, real-time only), `se-4b` (social engineering), `mw-4b`, `uws-4b`, `uwsa-4b`, `pha-4b`. Delivered Golomb-Rice-encoded with incremental updates and checksums. — [Google, "Local Database"](https://developers.google.com/safe-browsing/reference/Local.Database)
- v5 shifts "to be check-by-default instead of the allow-by-default protocol previously available in V4". The OHTTP relay is optional, and with it "end users' IP addresses are no longer sent to Google". `urls.search` sends raw URLs and is not confidential. The overview says the API "is free for non-commercial use and requires clear user warnings with specific language and attribution to Google." — [Google, Safe Browsing API v5 overview](https://developers.google.com/safe-browsing/reference)
- v4 Update API returns `minimumWaitDuration` (example "593.440s") and positive/negative cache durations. — [Google, Safe Browsing v4 Update API](https://developers.google.com/safe-browsing/v4/update-api)
- Apple Live Caller ID Lookup "uses homomorphic encryption to send an encrypted query to a server that can provide information about a phone number without the server knowing the specific phone number", built on Private Information Retrieval. Apple open-sourced `swift-homomorphic-encryption` and an example PIR backend (`live-caller-id-lookup-example`). — [Swift.org, "Announcing Swift Homomorphic Encryption" (Jul 2024)](https://swift.org/blog/announcing-swift-homomorphic-encryption/)
- Cloudflare: the "OHTTP Relay (formerly Privacy Gateway)" is Enterprise-only and "currently in closed beta". The relay sees client IP and request metadata, and logs are kept ~124 days. — [Cloudflare docs, OHTTP Relay](https://developers.cloudflare.com/ohttp-relay/); [legal](https://developers.cloudflare.com/ohttp-relay/reference/legal/). Oct 2026: a Cloudflare OHTTP Gateway closed beta "will not decrypt requests that reach it from Cloudflare Workers or from hosts proxied through Cloudflare". Relay and gateway must be run by different operators. — [InfoQ, "Cloudflare OHTTP gateway" (Oct 2026)](https://infoq.com/news/2026/10/cloudflare-ohttp-gateway)

### Inferences
- Shoo can apply the GSB pattern to its own lists without new permissions. Ship hashed allow/block lists in `storage.local` (with `unlimitedStorage` if over 5 MB). On device, compute SHA-256 of the eTLD+1 and up to 4 host suffixes. Query the Worker with 4-byte prefixes (plus random decoys) only when the local list misses. The Worker would then never see the domain for most lookups. Today the privacy rule allows sending the registrable domain. Hash-prefix lookup would let Shoo go further for blocklist checks.
- Hash prefixes cannot help for layer 3/4 checks that need the real domain (RDAP age, LLM reality check). Those must still send the eTLD+1. To hide the user's IP from the Shoo Worker, the options are a third-party OHTTP relay (Fastly-style, separate operator) or Apple-style PIR. Both are heavy for a student-team v1, and Cloudflare's own offering is gated and Worker-incompatible as a gateway.
- Using GSB v5 directly from Shoo's server is constrained by the "non-commercial" terms. A commercial product would need Google's paid product (Web Risk). That is not verified here.

### Gaps
- Google Web Risk terms/pricing for commercial use not fetched.
- No measured latency or cost of HE-PIR lookups at blocklist scale on iPhone found.
- Whether a Safari extension can reach an OHTTP relay (binary HPKE-encapsulated `message/ohttp-req` bodies via `fetch`) has not been tested. It should work from the background, but no report exists.

## Q6. Layered / cascade architectures: measured cost and accuracy trade-offs

### Takeaway
Every large deployed system is a cascade (local cache or list → server; local model → server verdict; heuristic trigger → on-device LLM → server). But I found no peer-reviewed paper that measures the cost/accuracy curve of a "cheap on-device first, LLM only when uncertain" phishing cascade. The best quantitative anchors are the components: local checks at ~100 ms (Chrome M92), server LLM stages at ~1.2–7 s and ~USD 1–6 per 1K pages (in `visual_llm.md`), and the share of traffic that reaches the expensive stage.

### Cited Findings
- GSB v5 Real-Time is a two-stage cascade. A local Global Cache hit means no network call, and only misses go to the server. — [Google, Real-Time Mode](https://developers.google.com/safe-browsing/reference/Real.Time.Mode)
- Chrome CSD is a two-stage cascade. A local content/visual model flags the page, then sends the URL + ~21 attributes to GSB, which decides on blocklisting. Its weak first stage (14% detection, 34% never classified) caps the whole cascade. — [Pourmohamad et al., AsiaCCS 2024](https://adamdoupe.com/publications/client-side-anti-phishing-asiaccs2024.pdf)
- Chrome Gemini Nano is a three-stage cascade. A heuristic trigger (e.g. Keyboard Lock API) invokes the on-device LLM, and its signals go to Safe Browsing for the verdict. — [BleepingComputer (May 2025)](https://www.bleepingcomputer.com/news/security/google-chrome-to-use-on-device-ai-to-detect-tech-support-scams/)
- Edge Scareware Blocker is two-stage. A local ML model handles detection and optionally reports to SmartScreen. — [Microsoft feature page](https://www.microsoft.com/en-us/edge/features/scareware-blocker)
- **[non-authoritative, practitioner]** A URL detector design where the classifier handles most traffic and the LLM sees only the ambiguous middle band, "roughly 20% of URLs". Not peer reviewed. — [DEV Community, "Building an AI-powered phishing URL detector"](https://dev.to/ayinedjimi-consultants/building-an-ai-powered-phishing-url-detector-2bph)
- LLM-stage cost/latency anchors (PhishLLM median USD 6.14/1K and 1.22 s; small open models F1 0.86–0.89) are in `visual_llm.md` §3 and not repeated here.

### Inferences
- For Shoo the cascade budget is set by traffic share. If layer 1–2 on device clear ~95%+ of page loads (most visits are to popular, allow-listed domains), layer 3 (RDAP, rules) runs on ≤5%, and layer 4 (LLM) only on layer-3 "uncertain". Then LLM cost scales with that small residue. A Global-Cache-style allowlist of popular registrable domains on device (as in GSB v5) is the cheapest lever to shrink server traffic and the data sent.
- The weakest-first-stage lesson from Chrome CSD is that the on-device stage must fail open to "send to server" (uncertain), never to "safe", when it times out or cannot parse the page. GSB's No-Storage mode returns SAFE on network error. Shoo should decide on purpose which way each failure falls.

### Gaps
- No peer-reviewed measurement of escalation rate, end-to-end latency, or detection lift for an on-device → server → LLM phishing cascade. Shoo will need to log its own escalation rates (per layer, with privacy-safe counters) to tune thresholds.
