# Page-content (HTML/DOM), HTTP-header, redirect-chain and cloaking features for phishing / scam site detection — effectiveness and iOS Safari feasibility

Scope note: research done 26 Oct 2026 for Shoo (iOS Safari Web Extension, MV3, plus a Cloudflare Workers server layer). Shoo today sends url, domain, title, lang, visible text (20k chars), form fields (type/name/id/label/placeholder/autocomplete/accept/capture/action; action collected but unused), and image alt texts. It does not inspect scripts, iframes, links, headers, or redirects. Older findings (before 2019) are flagged "[older]". Where a number came only from a search snippet or abstract, that is stated.

## Q1. Which HTML/DOM features rank highest, and how much do DOM features add over URL-only?

### Takeaway
The same small set of "abnormal-based" DOM features keeps ranking high across datasets: share of links/resources pointing to other domains (URL_of_Anchor, Request_URL, NoOfExternalRef/NoOfSelfRef/NoOfEmptyRef), where the form submits (SFH / form action), and password / hidden fields. But public benchmark numbers (often 97–99%+) are inflated by dataset artifacts. On PhiUSIIL a URL-only model already reaches ~99.5%, so measured DOM "lift" there is small. The lift is real where URLs look clean (compromised or free-hosting sites). Visual/intent systems (PhishIntention) focus on the credential-requiring page (CRP) plus brand, not hand-crafted DOM counts.

### Cited Findings
- [older, 2012] Mohammad, Thabtah & McCluskey defined the UCI "Phishing Websites" feature set, which includes HTML features: Request_URL (share of embedded objects loaded from another domain), URL_of_Anchor (share of `<a>` going to another domain or to nothing such as `#` / `javascript:void(0)`), Links_in_tags, SFH (Server Form Handler: empty or `about:blank` = phishing, other domain = suspicious), Submitting_to_email (`mailto:`), abnormal URL, on_mouseover, RightClick disabled, popUpWindow, Iframe. — [UCI Phishing Websites dataset](https://archive.ics.uci.edu/dataset/379/phishing+websites); [Mohammad, Thabtah, McCluskey, "An assessment of features related to phishing websites using an automated technique", ICITST 2012](https://pure.hud.ac.uk/en/publications/an-assessment-of-features-related-to-phishing-websites-using-an-a/)
- [older] A later review of this work reports that the authors found "Request URL" and "HTTPS and SSL" the most significant features (secondary source; original ranking table not seen). — [Fuzzy Rough Set Feature Selection to Enhance Phishing Attack Detection, arXiv 1903.05675, 2019](https://arxiv.org/pdf/1903.05675)
- A fuzzy-rough-set feature-selection study found the "abnormal-based" features (Request URL, URL of Anchor, SFH, etc.) to be "universally applicable" across all datasets it tested. — [arXiv 1903.05675, 2019](https://arxiv.org/pdf/1903.05675)
- PhiUSIIL (Prasad & Chandra, Computers & Security vol. 136, 2024): 134,850 legitimate + 100,945 phishing URLs. The framework downloads each page to extract HTML features. Features include NoOfImage, NoOfCSS, NoOfJS, NoOfSelfRef, NoOfEmptyRef, NoOfExternalRef, HasSocialNet, HasSubmitButton, HasHiddenFields, HasPasswordField, plus derived URLTitleMatchScore (title/brand vs URL), URLSimilarityIndex, CharContinuationRate, TLDLegitimateProb. — [PhiUSIIL, Computers & Security 136 (2024), DOI 10.1016/j.cose.2023.103545](https://dl.acm.org/doi/10.1016/j.cose.2023.103545); [UCI PhiUSIIL dataset page](https://archive.ics.uci.edu/dataset/967/phiusiil+phishing+url+dataset)
- Unreviewed replications on PhiUSIIL: (a) a URL-only XGBoost reaches ~99.5% accuracy on 235,370 deduplicated rows, so headroom for HTML features is small on this dataset; (b) an ablation finds almost all gain comes from "page-consistency" features (e.g., number of external references), and notes PhiUSIIL's "browser behaviour" columns are extracted from static HTML, not a live browser; (c) another project reports URL-only 90.25% vs URL+HTML 97.50% (+7.25 pp) with 32 URL + 33 HTML features. Treat all as non-peer-reviewed. — [GitHub nikhi20-900/phishing-url-detection](https://github.com/nikhi20-900/phishing-url-detection); [GitHub rimzim-r/phishing-detection-browser-behavior](https://github.com/rimzim-r/phishing-detection-browser-behavior); [GitHub JOEY20040407/Phishing-Website-Detection](https://github.com/JOEY20040407/Phishing-Website-Detection)
- Cross-dataset transfer is weak: training on one phishing-URL dataset and testing on another with SHAP shows features are "often dataset-dependent", even when they look similar across datasets (no numbers in abstract). — [Mia, Derakhshan, Pritom, "Can Features for Phishing URL Detection Be Trusted Across Diverse Datasets? A Case Study with Explainable AI", NSysS 2024 / arXiv 2411.09813](https://arxiv.org/abs/2411.09813)
- Peer-reviewed URL+HTML work: char-level TF-IDF over noisy HTML parts and plaintext plus hyperlink features (no clean URL-only ablation visible in snippet). — [Aljofey et al., "An effective detection approach for phishing websites using URL and HTML features", Scientific Reports 12, 2022](https://www.nature.com/articles/s41598-022-10841-5)
- PhishIntention (Liu et al., USENIX Security 2022) splits detection into brand intention (logo/brand vs domain) and credential-taking intention: a CRP classifier decides if the page asks for credentials; if not, a CRP locator predicts which UI element leads to a CRP and emulates the click (dynamic analysis). — [Liu et al., "Inferring Phishing Intention via Webpage Appearance and Dynamics: A Deep Vision Based Approach", USENIX Security 2022](https://www.usenix.org/system/files/sec22-liu-ruofan.pdf); [GitHub lindsey98/PhishIntention](https://github.com/lindsey98/PhishIntention)
- Follow-ups in the same reference-based line: KnowPhish (USENIX Security 2024, LLM + multimodal brand knowledge graph), PhishIntel (practical deployment, 2024), PhishAgent (2024). — [KnowPhish slides, USENIX Sec 2024](https://www.usenix.org/system/files/usenixsecurity24_slides-li-yuexin.pdf); [PhishIntel, arXiv 2412.09057](https://arxiv.org/pdf/2412.09057); [PhishAgent, arXiv 2408.10738](https://arxiv.org/pdf/2408.10738)
- Phishing pages share only ~11% of their browser APIs (on average) with the real brand login pages they copy, i.e., behaviour of scripts differs strongly from the original. — [Nahapetyan, Khare, Schwarz, Reaves, Kapravelos, "Characterizing phishing pages by JavaScript Capabilities", arXiv 2509.13186 (v2 2026)](https://arxiv.org/html/2509.13186v2)
- Obfuscation on phishing pages: ~21% of JS-behaviour clusters (1,991) use obfuscation, mostly `atob` (1,455 clusters) and `eval` (982); dynamic `<script>` creation in 1,092 clusters (16,859 pages); ~24% of pages (47,189) call deprecated APIs. Dataset: ~1.33M phishing URLs, Aug 2023–Jan 2025. No benign baseline, so FP rate of these as features is unknown. — [arXiv 2509.13186](https://arxiv.org/html/2509.13186v2)
- CrawlPhish observed JS code obfuscation on phishing sites rising from 20.79% (2018) to 24.04% (2019). — [Zhang et al., "CrawlPhish: Large-scale Analysis of Client-side Cloaking Techniques in Phishing", IEEE S&P 2021](https://kapravelos.com/publications/crawlphish-sp21.pdf)

### Inferences
- Highest-value cheap DOM features for Shoo's content script (all readable in-page): (1) form action host vs page host and empty/`about:blank`/`mailto:` actions; (2) password / OTP / card fields present (Shoo already has these); (3) ratio of `<a href>` to other registrable domains and to `#`/`javascript:`/empty; (4) ratio of `<script src>`, `<img src>`, `<link href>` (incl. favicon) from other domains; (5) title / logo-alt / visible brand vs registrable domain mismatch (URLTitleMatchScore-like). These are the features that keep ranking high from UCI (2012) to PhiUSIIL (2024).
- Do not trust single-dataset accuracy numbers for choosing features. PhiUSIIL-style 99%+ mostly reflects URL artifacts. Evaluate on Shoo's own Indonesian scam samples.
- "External resource ratio" is a weak signal alone for modern legit sites (CDNs, analytics, SSO). It works better relative to the brand being impersonated (e.g., page claims "BCA" but loads from neither BCA nor a known CDN).
- Obfuscation (`atob`/`eval`) is common on legit sites too (bundlers, ad tech); use it only as a weak, combined feature.

### Gaps
- Could not retrieve exact numbers for CANTINA+ (Xiang et al., ACM TISSEC 2011 [older]), HTMLPhish (Opara et al., 2020) or WebPhish (Opara et al.) — their feature-importance / ablation tables were not found in this session.
- No original PhiUSIIL feature-importance table seen; the paper's own ablation of HTML vs URL features is unverified.
- No peer-reviewed study found that measures URL-only vs URL+DOM lift specifically on mobile or on Indonesian/ID-language scam sites.

## Q2. Does "form action to another domain" / "password field over HTTP" still discriminate? Effect of fetch/XHR and Telegram-bot exfiltration

### Takeaway
SFH / form-action is a classic top feature, but modern kits increasingly send data via JavaScript (fetch/XHR to a PHP endpoint or directly to the Telegram Bot API), so the `<form action>` attribute is often empty, `#`, or same-origin. Ironically, the UCI definition treats an empty/`about:blank` action as phishing, so "empty action + password field + JS submit handler" remains a usable signal. "Password over HTTP" has lost power because most phishing now uses HTTPS (free certificates), though no single recent figure was found in this session.

### Cited Findings
- [older] UCI SFH rule: empty or `about:blank` form handler = phishing; handler on a different domain = suspicious; `mailto:` submission is a separate feature. — [UCI Phishing Websites dataset](https://archive.ics.uci.edu/dataset/379/phishing+websites)
- PhiUSIIL keeps HasSubmitButton, HasHiddenFields, HasPasswordField as HTML features (2024). — [UCI PhiUSIIL page](https://archive.ics.uci.edu/dataset/967/phiusiil+phishing+url+dataset)
- Ousat, Tofighi, Schafir, Kharraz analysed 1,300 phishing kits (2020–2023): "heavy reliance on current messaging services" for exfiltration; 284 kits (21.8%) used no evasion. They polled the kits' Telegram bots every 3 hours for 101 days and captured 8,635 messages containing username/password pairs, SMS 2FA codes and card details; one kit used a Discord channel. Key page components were "very similar or even identical across kits". (Abstract + snippet; per-channel shares not seen.) — [Ousat et al., "An Analysis of Architectural and Operational Dynamics of Phishkits in the Wild", arXiv 2608.07451, Aug 2026](https://arxiv.org/abs/2608.07451)
- "Leaky Kits" (APWG eCrime 2022): 4,238 distinct kits (from 26,281 archives over 15 months); 3.9% contained a backdoor; hard-coded Telegram bot tokens were found, and chat invite links exposing victims' PII were recovered in 0.5% of kits. (snippet) — [Leaky Kits: The Increased Risk of Data Exposure from Phishing Kits, APWG eCrime 2022](https://docs.apwg.org/ecrimeresearch/2022/2023095656.pdf)
- Vendor reports (non-academic) describe modern kits as platforms with admin panels and real-time credential delivery to Telegram bots, MFA-bypass proxies; credentials sent directly to attacker Telegram bots using configurable token + chat ID. — [Flare, "Phishing Kits: An Interactive Deep Dive"](https://flare.io/learn/resources/blog/phishing-kits-an-interactive-deepdive); [KnowBe4 blog](https://blog.knowbe4.com/cybercriminals-use-telegram-bots-to-exfiltrate-data-in-phishing-kit-campaign); [SonicWall blog](https://www.sonicwall.com/blog/threat-actors-caught-using-telegram-bot-to-harvest-credentials)
- Large-scale JS study: ~92% of phishing JS-behaviour clusters attach DOM event / click handlers; fingerprint exfiltration via fetch/XHR is described only as "uncommon" (no figure); Telegram exfil not measured. — [arXiv 2509.13186](https://arxiv.org/html/2509.13186v2)

### Inferences
- Shoo already collects `action`. Use it as: (a) action host ≠ page registrable domain → suspicious; (b) action empty / `#` / `javascript:` / `about:blank` while the form has password/OTP/card/PIN fields → suspicious (the UCI rule, now matching JS-submit kits); (c) `mailto:` → strong.
- For JS-submit kits, a content script can statically scan inline/same-origin script text for `api.telegram.org`, `/bot<digits>:` token patterns, `discord.com/api/webhooks`, or `sendMessage?chat_id=`. This is a high-precision fingerprint (legit login pages almost never talk to the Telegram Bot API from the browser). Feasible in iOS Safari: inline `<script>` text and same-origin external scripts are readable from a content script; cross-origin script bodies are not readable without a fetch (subject to CORS). Note: server-side kits that relay to Telegram from PHP leave no client trace.
- Watching actual outgoing requests (fetch/XHR destination) would need `webRequest` (observational; see Q3 feasibility) or monkey-patching `fetch`/`XMLHttpRequest` in the page's main world. Main-world injection in Safari is possible via an injected `<script>` element but is fragile and raises privacy review concerns; treat as a later option.
- "Password over HTTP" is now a low-yield but near-zero-FP-cost rule (Safari itself warns on HTTP password fields); keep as a minor feature only.

### Gaps
- No 2019–2026 peer-reviewed figure found for the share of phishing kits that submit via fetch/XHR vs `<form action>` vs Telegram, or for the share of phishing on HTTPS. Ousat et al. full text (per-channel shares) not read.
- No measured precision/recall for a "Telegram API string in page script" detector found.

## Q3. Are HTTP response headers and redirect-chain features used in research, how effective, and can Shoo observe them on iOS Safari?

### Takeaway
Header and redirect features appear in research but far less than URL/HTML features, and evidence is thinner (one 2024 header-only paper reports ~97.8% accuracy; redirect-graph work needs many chains). On iOS Safari the picture changed in 2024–2025: MDN compat data says `webRequest` is available on iOS Safari 18 (observational only), with `onHeadersReceived`/`onBeforeRequest` fully (incl. `extraInfoSpec`) from iOS 18.4, and `onBeforeRedirect` exposing `redirectUrl`, `statusCode` and `responseHeaders`. Blocking is not supported. Apple's own compatibility page is more restrictive (says blocking not supported and `opt_extraInfoSpec` not supported; implies `webRequest` is macOS-only), so the two sources conflict and Shoo must test on a device. From page JS, cross-origin redirect hops are effectively invisible.

### Cited Findings
- Header-only detector: 16 novel HTTP-header features (mainly security headers), 97.8% accuracy, 1.57 s mean response time; another listing reports 99.7% with Random Forest (figures differ between listings). — [Shukla et al., "HTTP header based phishing attack detection using machine learning", Transactions on Emerging Telecommunications Technologies, 2024, DOI 10.1002/ett.4872](https://onlinelibrary.wiley.com/doi/abs/10.1002/ett.4872)
- [older, 2018] Niakanlahiji et al. found presence/absence of certain header fields, number of header fields and number of non-standard header fields useful (cited via search snippet only). — reported in [search snippet referencing Shukla 2024 / ResearchGate](https://www.researchgate.net/publication/374257906_HTTP_header_based_phishing_attack_detection_using_machine_learning)
- Web-server fingerprinting from Transformer-encoded HTTP response headers (general, not phishing-specific) shows headers carry server/stack identity. — [Fingerprinting web servers through Transformer-encoded HTTP response headers, arXiv 2404.00056, 2024](https://arxiv.org/pdf/2404.00056)
- Attackers used the HTTP `Refresh` response header to forward victims to credential-harvesting pages in large campaigns (2024). — [The Hacker News, Sep 2024](https://thehackernews.com/2024/09/cybercriminals-exploit-http-headers-for.html)
- Ousat et al. list "dynamic redirection" and traffic attribution among kit evasion mechanisms. — [arXiv 2608.07451](https://arxiv.org/abs/2608.07451)
- iOS Safari support per MDN browser-compat-data (fetched 26 Oct 2026, `webextensions/api/webRequest.json`, `webNavigation.json`, `declarativeNetRequest.json`): `webRequest` safari_ios 18; `onBeforeRequest`, `onBeforeSendHeaders`, `onHeadersReceived`, `onResponseStarted`, `onCompleted`, `onSendHeaders` full from iOS 18.4 (iOS 18–18.3 partial: "`extraInfoSpec` options are not supported"); `onBeforeRedirect` iOS 18 with `details.redirectUrl`, `statusCode`, `statusLine`, `responseHeaders`, `ip`; `onHeadersReceived.details.responseHeaders` iOS 18; `BlockingResponse` not supported; macOS Safari 14–17 support was "Only worked with Manifest V2 extensions using persistent background content". `webNavigation` iOS 15 (onBeforeNavigate, onCommitted, onDOMContentLoaded, onCompleted, onErrorOccurred); `onHistoryStateUpdated`, `onCreatedNavigationTarget`, `transitionType`/`transitionQualifiers` not supported. `declarativeNetRequest` Safari 15 (iOS mirrors macOS); `Redirect`, dynamic/session rules from 15.4. — [MDN browser-compat-data, webRequest.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/webRequest.json); [webNavigation.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/webNavigation.json); [declarativeNetRequest.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/declarativeNetRequest.json)
- Apple "Assessing your Safari web extension's browser compatibility": `background` — "In iOS, you need to set the `persistent` attribute to `false`. With manifest version 3, all background pages are nonpersistent." `permissions.webRequestBlocking` — "Not supported. Use `permissions.webRequest` instead for macOS only." `webRequest` — "`BlockingResponse` not supported. Blocking requests not supported. `opt_extraInfoSpec` not supported for any of the events." `webNavigation` — `onCreatedNavigationTarget`, `onReferenceFragmentUpdated`, `onTabReplaced`, `onHistoryStateUpdated`, `transitionType`, `transitionQualifiers` not supported. `scripting.executeScript` — `allFrames`, `frameIds` not supported. (Apple doc conflicts with MDN on `extraInfoSpec` and possibly iOS availability; Apple page may lag.) — [Apple Developer, Assessing your Safari web extension's browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)
- declarativeNetRequest in Safari since Safari 15 (WWDC21); on iOS extensions must use a non-persistent background. WWDC22: up to 50 static rulesets, 10 enabled at once. WWDC26: block/modify/redirect; redirects need `declarativeNetRequestWithHostAccess` plus host permission. Developer forum reports: redirect failing on Safari 15.1, `modifyHeaders` not working on macOS Safari 17.1, stale `getMatchedRules()` on iOS 18 (anecdotal). DNR cannot read response headers; it only matches requests. — [WWDC21 10027](https://developer.apple.com/videos/play/wwdc2021/10027/); [WWDC22 10099](https://developer.apple.com/videos/play/wwdc2022/10099/); [WWDC26 216](https://developer.apple.com/videos/play/wwdc2026/216/); [Apple forums 713662](https://developer.apple.com/forums/thread/713662); [Apple forums 760969](https://developer.apple.com/forums/thread/760969)
- Navigation/Resource Timing: Chromium hides `redirectCount`/`redirectStart`/`redirectEnd` when a navigation's redirect chain has cross-origin hops; WebKit exposes them only when every response in the chain carries `Timing-Allow-Origin`. A 2026 proposal (whatwg/fetch PR 1931) would expose them when TAO is `*` or names the destination. MDN: zero `redirectStart/End` can mean cross-origin without TAO. — [blink-dev "Intent to Ship: Cross-origin redirect timing opt-in"](https://groups.google.com/a/chromium.org/g/blink-dev/c/BDdFJLzB4Do); [MDN PerformanceResourceTiming.redirectStart](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/redirectStart)

### Inferences
- Feasibility matrix for Shoo (iOS Safari Web Extension):

| Feature | Source in iOS Safari | Feasible? |
|---|---|---|
| Form action host, password/OTP fields, hidden inputs | content script DOM | Yes (already partly collected) |
| Link / resource / favicon external ratio, `#`/null links | content script DOM (`a[href]`, `script[src]`, `img`, `link[rel~=icon]`) | Yes |
| Iframe count, hidden elements, right-click/copy disabled | content script DOM + computed style; `oncontextmenu`/`oncopy` attributes, `user-select:none` | Yes (same-origin iframe contents only; cross-origin iframe = `src` only) |
| Inline script text (Telegram/Discord strings, `atob`/`eval`, devtools traps) | content script reads `script.textContent` | Yes for inline; same-origin external via fetch; cross-origin external limited by CORS |
| Runtime JS behaviour (actual fetch/XHR targets) | main-world injection or `webRequest` | Partial / fragile |
| Response headers (Server, X-Powered-By, CSP, HSTS, Set-Cookie, cache) of main document | `webRequest.onHeadersReceived` / `onCompleted` `responseHeaders` | Per MDN: iOS 18+ (full extraInfoSpec 18.4+), observational; per Apple doc: unclear/macOS-only → must test on device. Needs host permission for all sites and an event-driven non-persistent background. |
| Redirect chain (hops, status 301/302, shorteners) | `webRequest.onBeforeRedirect` (`redirectUrl`, `statusCode`) | Same caveat as above; fallback: `webNavigation.onBeforeNavigate`/`onCommitted` sequence in tab (sees navigations, incl. JS/meta-refresh, but not HTTP 3xx hops) |
| Redirect count from page JS | `performance.getEntriesByType('navigation')[0].redirectCount` | Only same-origin or TAO-opted chains → cross-origin phishing hops show 0. Low value. |
| Meta-refresh / JS redirect on current page | content script: `meta[http-equiv=refresh]`, `location.replace`/`window.location=` in inline scripts | Yes (static) |
| Referrer | `document.referrer` | Yes, but often stripped by referrer policy; weak |
| Block/redirect before load | declarativeNetRequest (dynamic rules) | Yes, list-based only; cannot use headers |

- Because Shoo's server may only receive the registrable domain, header/redirect features are best computed on-device (if `webRequest` works on target iOS versions) and only summarised features (e.g., `redirect_hops=3`, `has_shortener=true`, `server=…`) sent up — not full URLs. This keeps the privacy rule.
- Server refetch from Cloudflare Workers of `https://<registrable-domain>/` gives headers/redirects of the root only, not the phishing path; plus Workers egress IPs are datacentre IPs (a classic cloaking trigger — see Q4). So server-side header features will be biased toward the cloaked/benign view.
- Header features likely add little over DOM/URL for Shoo; the one cheap, high-signal item is the redirect chain (shortener → free host → kit) when observable.

### Gaps
- Could not verify on-device whether `webRequest` events fire for main-frame navigations in iOS 18.4+/iOS 26 Safari under MV3 non-persistent background (MDN vs Apple doc conflict). Needs a device test.
- No peer-reviewed 2019–2026 study found that quantifies redirect-chain features (hop count, shortener use) for phishing classification with precision/recall; only a graph-based approach that needs many chains and an unreviewed student report (phishing ≥4 redirects vs legit 1) surfaced.
- No study found that fingerprints phishing kits via HTTP headers specifically.

## Q4. How common is cloaking today, and how does it affect server-side crawling vs client-side (in-browser) detection?

### Takeaway
Cloaking is mainstream: client-side cloaking on ~31% of phishing sites in 2018–19 (growing 23%→34%), server-side filters (IP/UA/geo/referrer, .htaccess) cut blocklisting by ~53–55%, and 2023–25 kits add fingerprinting (~70–80% of JS clusters), timing checks (~22%), client-side IP reputation, and CAPTCHA/Turnstile gates. This strongly favours in-browser detection (Shoo's content script sees exactly what the victim sees, after any gate is passed) over server refetch (datacentre IP, no user interaction, and Shoo's server only knows the domain).

### Cited Findings
- CrawlPhish (Zhang, Oest, et al., IEEE S&P 2021): 112,005 phishing sites over 14 months (2018–2019); 35,067 (31.3%) used client-side cloaking with 1,128 distinct implementations; cloaking grew from 23.32% (2018) to 33.70% (2019). Taxonomy: User Interaction (pop-up/notification, alert, mouse detection, click-through incl. fake reCAPTCHA), Fingerprinting (cookie, referrer, user-agent), Bot Behaviour (timing, randomization). Mouse detection = 16.53% of implementations. Detector FP 1.45%, FN 1.75%. — [CrawlPhish, IEEE S&P 2021](https://kapravelos.com/publications/crawlphish-sp21.pdf)
- CrawlPhish field test: 150 PayPal-branded cloaked test sites (50 each: notification, click-through fake CAPTCHA, mouse detection) reported to GSB, PhishTank, Netcraft, APWG, PayPal, US-CERT: after 7 days none were blacklisted in Chrome/Opera/Edge, except 21 (42%) click-through sites blocked by Edge (SmartScreen flagged JS obfuscation as malware, not by defeating the cloak). User study: mouse-detection and click-through content was seen by 100% and 97.72% of users, notification-window by 42.55% — i.e., cloaking barely hurts victims. — [CrawlPhish, IEEE S&P 2021](https://kapravelos.com/publications/crawlphish-sp21.pdf)
- PhishFarm (Oest et al., IEEE S&P 2019): 2,380 live phishing sites with 6 server-side request filters from real kits (A none; B mobile-UA only; C US-desktop GSB browsers; D non-US desktop; E block known security entities by UA/referrer/hostname/IP, based on top .htaccess kit filters; F JS-capable browsers only). Cloaked sites were blacklisted 23.0% vs 49.4% uncloaked (~53% relative drop; abstract: ">55% on average"). Mobile-only (B) sites were never blacklisted; mobile Chrome/Safari/Firefox showed no warnings at all until fixes after disclosure (2018). Earliest blacklisting ~40 min; mean first blacklisting 126 min uncloaked vs 238 min cloaked. — [Oest et al., "PhishFarm: A Scalable Framework for Measuring the Effectiveness of Evasion Techniques against Browser Phishing Blacklists", IEEE S&P 2019](https://adamdoupe.com/publications/phishfarm-oakland2019.pdf); [IEEE Xplore 8835369](https://ieeexplore.ieee.org/document/8835369/)
- Sunrise to Sunset (Oest et al., USENIX Security 2020, Distinguished Paper): Golden Hour framework saw 4.8M victims over one year; average campaign ~21 h from start to last victim; ≥7.42% of visitors were compromised with a fraudulent transaction; a few campaigns accounted for 89.13% of victims. — [USENIX Security 2020 presentation page](https://www.usenix.org/conference/usenixsecurity20/presentation/oest-sunrise); [paper PDF](https://www.usenix.net/system/files/sec20-oest-sunrise.pdf)
- 2023–2025 JS-capability study (~1.33M phishing URLs, Aug 2023–Jan 2025): basic fingerprinting ~80% of clusters (289,954 pages), advanced fingerprinting ~70%, timing-based bot detection (`performance.now` + `setTimeout`) ~22%, client-side IP-reputation checks in 412 clusters (19,778 pages) using 14 IP-intelligence APIs, mouse detection 28 clusters, Cloudflare Turnstile 9 clusters (184 pages) though prominent in campaign reports; cluster lifetime avg 39 days. Limitation: crawler does not interact, so multi-stage flows are missed. — [arXiv 2509.13186](https://arxiv.org/html/2509.13186v2)
- PhishInPatterns: CAPTCHA deployment evidenced on 2,608 of 51,859 phishing sites (~5.0%). — [PhishInPatterns: measuring elicited user interactions at scale on phishing websites](https://www.researchgate.net/publication/364718137_PhishInPatterns_measuring_elicited_user_interactions_at_scale_on_phishing_websites)
- PhishDecloaker (USENIX Security 2024) solves CAPTCHA gates during crawling; a 30-day field study uniquely discovered 7.6% more phishing sites cloaked by CAPTCHAs. — [PhishDecloaker, ACM DL 10.5555/3698900.3698929](https://dl.acm.org/doi/10.5555/3698900.3698929)
- PhishParrot (2025) uses an LLM-driven adaptive crawler to reach cloaked phishing pages, showing crawler-side cloaking remains an open problem. — [PhishParrot, arXiv 2508.02035](https://arxiv.org/pdf/2508.02035)
- Ousat et al.: 78.2% of 1,300 kits (2020–2023) used some evasion (284 = 21.8% used none), incl. traffic attribution and dynamic redirection. — [arXiv 2608.07451](https://arxiv.org/abs/2608.07451)

### Inferences
- For Shoo, cloaking is the strongest argument for the on-device (content-script) layer: the extension runs inside the user's real Safari, on a residential/mobile IP, with a mobile UA, after the user has passed any click-through/CAPTCHA/Turnstile gate. The DOM it reads is the real phishing page. PhishFarm's filter B (mobile-only) is exactly the traffic Shoo users generate.
- A gate page (fake reCAPTCHA, Turnstile, "click to continue") is itself a weak signal; combine with "next page asks for credentials on a non-brand domain". Re-run detection on DOM mutations / after navigation (`webNavigation.onCompleted`, `MutationObserver`) because content appears only after the gate.
- Server refetch from Cloudflare Workers is weak against cloaking: datacentre IP (filter E, IP-reputation APIs), no JS interaction (filter F, mouse detection), root path only (privacy rule), and Workers' own UA/TLS fingerprint. Expect it to see the benign/decoy view for a meaningful share of cloaked kits. Use server refetch only as a secondary signal (domain age, certificate, root headers), never to clear a page the device flagged.
- Client-side detection is also attackable: kits that fingerprint for extension artefacts or delay rendering (timing ~22%) could hide content until after Shoo's first scan. Rescanning after interaction mitigates this.

### Gaps
- Sunrise to Sunset's cloaking-specific results (full PDF) not read in this session.
- No 2023–2026 peer-reviewed number found for the overall share of phishing sites using server-side cloaking, or for Turnstile prevalence beyond the 9-cluster count.
- No study found measuring cloaking that targets mobile-Safari users specifically after 2019.

## Q5. Phishing-kit detection (kit fingerprints, Telegram exfiltration) — measured effectiveness

### Takeaway
Kits are highly reused, so fingerprinting works: a few kit families cover most deployments (10 Dutch families → 1,363 domains; 20% of cloaking implementation groups → ~75% of sites; browser-API-set clustering FMI 0.98). Behaviour-based fingerprints (API sets) beat static hashes. Telegram is now a dominant exfil channel; its token/chat strings are a strong in-page fingerprint when exfil is client-side.

### Cited Findings
- Bijmans et al. (USENIX Security 2021): 70 Dutch kits from underground markets → 10 kit families; kit fingerprints identified 1,363 Dutch phishing domains (Sep 2020–Jan 2021) found via TLS certificates; median domain uptime 24 h; only a few kits in use; decoy pages observed. — [Bijmans et al., "Catching Phishers By Their Bait: Investigating the Dutch Phishing Landscape through Phishing Kit Detection", USENIX Security 2021](https://www.usenix.org/conference/usenixsecurity21/presentation/bijmans)
- CrawlPhish: 20% of unique cloaking implementation groups account for 74.65% of cloaked sites — heavy reuse. — [CrawlPhish, IEEE S&P 2021](https://kapravelos.com/publications/crawlphish-sp21.pdf)
- Nahapetyan et al.: 4,180 pages with recovered kits → 885 kit families; clustering by browser-API sets reached Fowlkes-Mallows 0.98 (0.73 rebalanced), V-measure 0.92; script SHA-256 hashes only FMI 0.71–0.85; 434,495 pages → 9,306 clusters; 69% of clusters target one brand. — [arXiv 2509.13186](https://arxiv.org/html/2509.13186v2)
- Ousat et al.: kit components "very similar or even identical across kits"; reliance on "known tricks" makes many cases predictable; Telegram bot polling recovered 8,635 victim messages in 101 days. — [arXiv 2608.07451](https://arxiv.org/abs/2608.07451)
- Leaky Kits: 4,238 kits, 3.9% backdoored, hard-coded Telegram tokens common enough to recover victim chats in 0.5% of kits. — [APWG eCrime 2022](https://docs.apwg.org/ecrimeresearch/2022/2023095656.pdf)

### Inferences
- Shoo can implement a light kit-fingerprint layer on-device: hashes or token sets of inline script / DOM skeleton (form field names/ids, CSS class names, asset filenames) matched against a server-distributed list. Shoo already sends field names/ids/labels, which are classic kit fingerprints (kits reuse field `name`s like fixed Indonesian bank-login templates). This works inside the 20k-text payload without new permissions.
- Prefer behaviour/structure fingerprints over exact file hashes (hashes break with trivial edits, per the FMI comparison).
- Telegram-string detection is client-feasible only when exfil code ships to the browser; kits that POST to their own PHP and relay to Telegram server-side are invisible to any client.

### Gaps
- No measured precision/recall for a deployed kit-fingerprint detector on live traffic (most studies report clustering quality, not detection FP rates on benign pages).
- No Indonesia-specific kit study found (relevant for Shoo's target market).
- Concept drift: cluster lifetimes (avg 39 days) and kit evolution (obfuscation 20.79%→24.04%; AES-encrypted cloaking with keys in request params) imply fingerprint lists need frequent updates; no paper found that measures fingerprint decay rate directly.
