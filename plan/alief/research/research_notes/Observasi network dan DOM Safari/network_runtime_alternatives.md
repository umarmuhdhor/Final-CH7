# Observing network and runtime JS behaviour from an iPhone Safari Web Extension (and its containing app) without `webRequest`

Scope note: research done 26 Oct 2026 for Shoo (iOS Safari Web Extension MV3 + containing app with App Group + Cloudflare Workers). Manifest today: `nativeMessaging`, `storage`, `alarms`, content scripts on all http(s) hosts. Privacy rule: server gets only the registrable domain unless the user reports the page. Never collect typed values. This file extends `../Fitur deteksi situs phishing/safari_ios_deployment.md` and `html_headers_redirect.md`. It does not repeat their webRequest / declarativeNetRequest / webNavigation tables, the `redirectCount` cross-origin rule, the Safari 18.4 CORS note, GSB v5 / OHTTP / Live Caller ID PIR, the cloaking statistics, or the kit-fingerprint papers (Bijmans, CrawlPhish reuse, Leaky Kits). Version numbers such as "iOS 27" come from Apple's own doc metadata, fetched 26 Oct 2026.

## Q1. MAIN-world instrumentation from a content script: availability, timing, what hooks can see, evasion, and safe message passing

### Takeaway
MAIN-world hooks are the only in-browser way to see where a page's JavaScript sends data on iOS. They can be registered at `document_start` from iOS 16.4 (`scripting.registerContentScripts({world:'MAIN'})`), which is earlier than the manifest `world` key (iOS 18). A hook sees the destination URL, method and body type of every `fetch`/XHR/beacon/WebSocket the page makes from the main thread, before the request is sent. CORS does not hide those. It only limits response headers and status to what the page itself could read. Hooks are trivially detectable. Pages can also bypass them through Workers, fresh iframes and native form navigation. Messages from the MAIN world can be forged by the page. So treat a hook hit as positive evidence only, and never treat a missing hit as proof the page is benign.

### Cited Findings
**Availability (MDN browser-compat-data, fetched 26 Oct 2026)**
- `scripting.executeScript` + `world: MAIN`: Safari iOS 15.4. `scripting.RegisteredContentScript.world`: iOS **16.4**. `registerContentScripts` / `updateContentScripts` / `getRegisteredContentScripts`: iOS 16.4. `persistAcrossSessions`: 16.4. `matchOriginAsFallback`: 18.4. Manifest `content_scripts.world`: iOS 18. `match_about_blank` / `match_origin_as_fallback`: 18.4. `executeScript.injectImmediately` is partial ("Scripts are always injected immediately"). — [MDN BCD, webextensions/api/scripting.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/scripting.json); [MDN BCD, webextensions/manifest/content_scripts.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/content_scripts.json)
- Apple engineer, Apr 2023: "Safari 16.4 does support "MAIN" for registerContentScripts." The original poster had only tested on desktop. — [Apple Developer Forums thread 728849, "Support for world: MAIN in Safari web extension content scripts" (2023)](https://developer.apple.com/forums/thread/728849)
- Related WebKit fixes: an intermittent "Failed to add content script" error from `registerContentScripts()` was fixed in June 2025 (bug 294298). `excludeMatches` being ignored was fixed in April 2025 (bug 290858). — [WebKit Bugzilla 294298](https://bugs.webkit.org/show_bug.cgi?id=294298); [WebKit Bugzilla 290858](https://bugs.webkit.org/show_bug.cgi?id=290858)
- `navigator.sendBeacon`: Safari iOS 11.1. — [MDN BCD, api/Navigator.json](https://github.com/mdn/browser-compat-data/blob/main/api/Navigator.json)

**Timing (document_start)**
- Chrome's definition of `document_start`: "Scripts are injected after any files from `css`, but before any other DOM is constructed or any other script is run." Chrome also says: "When a content script is injected into the main world, the CSP of the page applies." — [Chrome for Developers, "Content scripts" (Google, current)](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)
- Safari caveat (BCD note on `run_at`): "Content scripts are not applied to tabs until the user grants permission via the extension's access alert. Additional loads after permission is granted will respect `run_at`." So the first load after a new grant is not hooked at `document_start`. — [MDN BCD content_scripts.json](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/content_scripts.json)
- A React DevTools developer described the same pattern on Chrome: register a MAIN-world script at `document_start` to patch the page before React loads. — [Mozilla Discourse, "Will scripting.ExecutionWorld.MAIN be supported?" (2023)](https://discourse.mozilla.org/t/will-scripting-executionworld-main-be-supported/112919)
- I found no WebKit document or bug that guarantees a Safari MAIN-world `document_start` script runs before inline page scripts.

**What a hooked `fetch`/XHR can read (Fetch response types)**
- `basic` (same-origin): "all response headers are exposed except `Set-Cookie`". `cors`: "only CORS-safelisted response headers are exposed". `opaque` (`no-cors`): "`status` property is set to `0`, `body` is `null`, headers are empty and immutable". `opaqueredirect` (`redirect: 'manual'`): the same, status 0 and no headers. — [MDN, Response.type (Mozilla, current)](https://developer.mozilla.org/en-US/docs/Web/API/Response/type)
- Content-script requests stay subject to CORS: "Cross-origin requests are always treated as such in content scripts, even if the extension has host permissions." — [Chrome for Developers, "Cross-origin network requests"](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)

**Message passing between the MAIN and ISOLATED worlds**
- The isolated world is "a private execution environment that isn't accessible to the page or other extensions". The two worlds "share access to the page's DOM" and must communicate "through the shared DOM" (`window.postMessage`). Chrome's sample filters with "We only accept messages from ourselves". It also warns that "using content scripts can create vulnerabilities in an extension and the web page". — [Chrome for Developers, "Content scripts"](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

**How pages detect or evade hooks**
- OpenWPM, a research crawler that wraps JS APIs in the page context, "is easily detectable". It was detected on ~14% of 100k front pages, and some scripts had routines aimed specifically at OpenWPM. The authors also found "previously unknown attacks against OpenWPM's instrumentation" that corrupt the recorded data. — [Krumnow, Jonker & Karsch, "How Gullible Are Web Measurement Tools? A Case Study Analysing and Strengthening OpenWPM's Reliability", ACM CoNEXT 2022, DOI 10.1145/3555050.3569131 — ACM, paywalled; open preprint arXiv 2205.08890](https://arxiv.org/abs/2205.08890)
- Phishing pages already fingerprint their environment. In 2023–25 crawls, basic fingerprinting appeared in 80% of kit clusters (289,954 pages) and advanced fingerprinting in 70%. Timing bot checks (`Performance.now` + timeout) appeared in 22%, and dynamic `<script>` creation in 1,092 clusters (16,859 pages). Obfuscation used `atob` (61,125 pages), `eval` (14,561), `TextDecoder.decode` (11,113) and `SubtleCrypto.decrypt` (1,185). — [Nahapetyan, Khare, Schwarz, Reaves & Kapravelos, "Characterizing Phishing Pages by JavaScript Capabilities", arXiv 2509.13186 (2025)](https://arxiv.org/html/2509.13186v2)
- Common detection tricks, from non-academic sources: `Function.prototype.toString.call(fn)` does not return "[native code]" for a wrapper. Wrong `fn.name`, `fn.length` or property descriptors also give it away. A fresh iframe's `contentWindow` provides unhooked built-ins. Counter-hooks patch the `HTMLIFrameElement.prototype.contentWindow` getter. — [Scrappey, "How toString reveals hooked functions" (vendor page, unverified)](https://scrappey.com/qa/reverse-engineering/how-tostring-reveals-hooked-functions); [David Walsh, "Detect if a Function is Native Code"](https://davidwalsh.name/detect-native-function); [Greasy Fork, "DevTools Anti-Detector" userscript](https://greasyfork.org/ko/scripts/41559-devtools-anti-detector/code)

### Inferences
- **Version plan for Shoo.** Use `browser.scripting.registerContentScripts([{id, js:['hook.js'], matches:['http://*/*','https://*/*'], runAt:'document_start', world:'MAIN', allFrames:true}])` from the background script. This works on iOS 16.4+ and needs the `scripting` permission, which Shoo's manifest does not have today. Alternatively, put `world: "MAIN"` in a second `content_scripts` entry, but that limits the hook to iOS 18+. The site-access prompt does not change, because Shoo already has all http(s) hosts. Adding `scripting` changes the permission list, so update the App Store privacy label and the review notes.
- **Hook surface and what each hook reveals.** Wrap `window.fetch` (URL, method, body type, `mode`). Wrap `XMLHttpRequest.prototype.open`/`send`. Wrap `navigator.sendBeacon` and the `WebSocket` constructor (URL). Wrap `HTMLFormElement.prototype.submit` and `requestSubmit`, and add a capture-phase `submit` listener. Wrap the `HTMLImageElement.prototype.src` setter for pixel beacons (via `Object.getOwnPropertyDescriptor`), and `window.open`. All of these run before the request leaves, so the destination is always visible. That holds even for an opaque `no-cors` request, a cross-origin POST, or a call to `api.telegram.org`. `location` assignment cannot be wrapped the same way, because `Location` properties are unforgeable. Detect it instead from the navigation itself (`pagehide`, or `webNavigation.onBeforeNavigate` in the background). The Navigation API's `navigate` event might also work, but its Safari support is unverified.
- **Response visibility.** A wrapped `fetch` gets the same `Response` object the page gets. That object exposes all headers except `Set-Cookie` for same-origin calls, only safelisted headers for CORS calls, and nothing (status 0) for `no-cors` calls. `response.redirected` and `response.url` are readable on non-opaque responses, and so is XHR `responseURL`. This gives same-origin redirect evidence for the page's own API calls, not for the top-level navigation.
- **Blind spots (structural).** MAIN-world scripts run only in documents. They do not see requests from Dedicated Workers, Shared Workers or Service Workers, so a kit can exfiltrate from a Worker. They also miss plain HTML `<form action>` navigations that are never wrapped, though the capture `submit` listener and the existing `action` feature cover those. Requests made before the hook installs are missed too, which includes the first load after a grant. Hooks can be undone by a fresh iframe realm unless `allFrames` plus `match_about_blank` (iOS 18.4) inject into same-origin `about:blank` frames as well.
- **Trust model.** The page can see and call everything in the MAIN world, so it can forge or drop messages. Accept MAIN-world messages only as one-way "evidence up" events in a fixed schema. Validate them in the ISOLATED world: check the type, cap the size, and match the expected `event.source === window` and `origin`. Treat them as add-only risk signals, such as `exfil_dest_offsite=true` or `telegram_api_call=true`. A phisher who forges these only incriminates itself. A phisher who suppresses them only reduces evidence, so never use "no exfil seen" to whitelist a page. A random per-load nonce does not help, because the page can read it in the MAIN world.
- **Privacy design (Apple guidance plus Shoo's rule).** The hook must not read request bodies, form values, headers or cookies. Emit only these: API kind; destination eTLD+1 (computed on device); flags such as offsite vs. same-site, known exfil service (`api.telegram.org`, `discord.com/api/webhooks`, form-to-email services), HTTP vs. HTTPS, and body kind (FormData/JSON/string length bucket). Timing can also be emitted, such as "request issued < 2 s after a `password`/OTP field `input` event". That uses only the event, never the value, which stays inside the "never collect typed values" rule. Aggregate these on device. The server keeps receiving only the page's registrable domain. The exfil destination goes up only in a user report.
- **Performance and compatibility risk.** Wrapping hot paths on every page can break sites that do their own feature detection, including legitimate anti-fraud SDKs that run `toString` checks. Prefer thin wrappers that call the original synchronously. Never modify arguments. Consider enabling the hook only after layer 1–2 flags a page as "uncertain" (call `executeScript` with `world:'MAIN'` at that point). The trade-off is that early-page requests are then missed.

### Gaps
- No Apple or WebKit statement that a Safari MAIN-world `document_start` script reliably runs before the first inline `<script>`. Needs a device test: register a hook, load a page with an inline `fetch` in `<head>`, and check whether it was intercepted.
- Whether page CSP blocks a Safari MAIN-world registered script. Chrome says page CSP applies to MAIN-world scripts, meaning `eval` inside them, but registered scripts are not blocked like inline `<script>`. Not documented for Safari.
- No source found on whether Safari applies MAIN-world registered scripts to `about:blank`/`srcdoc` frames created by script after load.
- No measured CPU or memory overhead for MAIN-world hooks on iOS Safari.

## Q2. `PerformanceObserver` / Resource Timing in Safari: which cross-origin details are visible

### Takeaway
Resource Timing is a passive, permission-free, unhookable-by-design list of what the page loaded. Even cross-origin, each entry gives the full resource URL (`name`) and `initiatorType` (script, img, xmlhttprequest, fetch, iframe, beacon...). Without `Timing-Allow-Origin` (TAO), timings, `nextHopProtocol` and the size fields come back as 0 or an empty string. Safari does not implement `responseStatus` at all, so status codes are never available. Entries appear after the response completes, so this is good for detection, not for blocking. It does not include Worker-initiated requests on iOS, and it does not include requests blocked by CSP/CORS/mixed content.

### Cited Findings
- Safari iOS support (MDN BCD): `PerformanceResourceTiming` 11. `initiatorType`, `nextHopProtocol`, `redirectStart`/`End`, `workerStart` 11. `transferSize`, `encodedBodySize`, `decodedBodySize` 16.4. `serverTiming` 16.4. `deliveryType`, `firstInterimResponseStart` and `finalResponseHeadersStart` 26.4. `workerRouterEvaluationStart`/`workerCacheLookupStart` 27. **Not supported in Safari:** `responseStatus` (Chrome 109), `contentType` (Chrome 148), `contentEncoding` (Chrome 143), `renderBlockingStatus`. `PerformanceResourceTiming.worker_support`: Safari macOS 12, **iOS false**. `PerformanceObserver` iOS 11. `supportedEntryTypes` 13. `takeRecords` 15. `droppedEntriesCount` not supported. — [MDN BCD, api/PerformanceResourceTiming.json](https://github.com/mdn/browser-compat-data/blob/main/api/PerformanceResourceTiming.json); [MDN BCD, api/PerformanceObserver.json](https://github.com/mdn/browser-compat-data/blob/main/api/PerformanceObserver.json)
- Fields zeroed without TAO: "`redirectStart`, `redirectEnd`, `domainLookupStart`, `domainLookupEnd`, `connectStart`, `connectEnd`, `secureConnectionStart`, `requestStart`, and `responseStart`." — [MDN, PerformanceResourceTiming (Mozilla, current)](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming)
- W3C Resource Timing: when the timing allow check fails, listed attributes "will always return zero or the empty string", and the list includes `nextHopProtocol`. `contentType`, `encodedBodySize` and `decodedBodySize` are zeroed (or empty) "when the response is CORS-cross-origin". `transferSize` is affected by both TAO and CORS. `responseStatus` is 0 for cross-origin `no-cors` (opaque). Network-error failures (DNS/TCP/TLS) are included with only `startTime`, `fetchStart`, `duration` and `responseEnd` set. Requests that fail a fetch precondition (mixed content, CORS, CSP) are not included. An iframe's `src` fetch appears in the parent timeline, and the iframe's own sub-resources appear in the iframe's timeline. — [W3C Web Performance WG, "Resource Timing" (Editor's Draft, current)](https://w3c.github.io/resource-timing/)
- The buffer holds 250 entries by default (implied). `performance.setResourceTimingBufferSize()` raises it, and `resourcetimingbufferfull` fires when it is full. — [MDN, "Resource timing" guide](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Resource_timing)
- Phishing pages often load first-party scripts or images from the targeted brand. Golden Hour used the brand's view of those loads to measure 4.8M victim visits. Campaigns lasted ~21 h on average, detection came ~9 h after the first victim, and ≥7.42% of visitors were compromised. — [Oest et al., "Sunrise to Sunset: Analyzing the End-to-end Life Cycle and Effectiveness of Phishing Attacks at Scale", USENIX Security 2020 (open access)](https://www.usenix.org/conference/usenixsecurity20/presentation/oest-sunrise)

### Inferences
- **Usable features from a content script with no new permission.** (a) The set of resource eTLD+1s and the share that are third-party (a runtime version of UCI `Request_URL`, but one that includes JS-loaded resources). (b) Resources loaded from a brand domain (e.g. `*.bca.co.id`, `paypalobjects.com`) while the page's eTLD+1 is not that brand. Per Oest et al., this is a strong phishing tell, and it works even when the HTML is obfuscated. (c) `initiatorType` `xmlhttprequest`/`fetch`/`beacon` entries to an off-site host after a credential field appears. This works as a fallback exfil signal when MAIN-world hooks are bypassed, though not for Worker requests on iOS. (d) Same-origin entries: `nextHopProtocol` (h2/h3) and `transferSize === 0` (cache). (e) Entries with only `responseEnd` set suggest a network error, for example a dead exfil host.
- **Limits.** No status codes (`responseStatus` is absent in Safari). No headers. No IPs. No DNS data. Redirect hops are zeroed cross-origin. Entries are created only after the response ends, so a final `sendBeacon` on `pagehide` may never be observed. Use `new PerformanceObserver(cb).observe({type:'resource', buffered:true})` at `document_start` so earlier entries are captured. Raise the buffer size for heavy pages.
- **Privacy.** `name` is a full URL with path and query, which can contain tokens or emails. Reduce it to eTLD+1 plus `initiatorType` on device, and never send raw entries.

### Gaps
- Not verified whether `performance.getEntriesByType('resource')` in a Safari **ISOLATED-world** content script returns the page's entries. Expected, because both worlds share the same `window.performance` implementation object. Needs a device test, and the MAIN world is a guaranteed fallback.
- Whether WebKit emits `initiatorType: "beacon"` for `sendBeacon` and `"fetch"` vs `"xmlhttprequest"`: not checked in WebKit source.
- No phishing paper found that measures detection gain from Resource Timing data collected in real users' browsers (crawler HARs only).

## Q3. Background-page `fetch` of the same URL: headers, redirects, cookies, cloaking

### Takeaway
A background `fetch` with host permission is not CORS-restricted on Chromium. It can read the status, all response headers except `Set-Cookie`, `response.redirected` and the final `response.url`. It cannot list intermediate hops: `redirect:'manual'` returns an `opaqueredirect` with status 0 and no `Location`. On Safari 18.4+, a `permissions.request` call must come first (prior notes). It runs from the user's own IP and device, so it beats a Cloudflare datacenter fetch against IP-based cloaking. But it executes no JS, may send no or different cookies, and makes a second request to the attacker's server. That second request can confirm a live victim or burn a one-time link.

### Cited Findings
- Background or extension pages "can talk to remote servers outside of its origin, as long as the extension requests host permissions". Content scripts get no such exemption. — [Chrome for Developers, "Cross-origin network requests"](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)
- `basic` responses expose "all response headers ... except `Set-Cookie`". `opaqueredirect` is "a response to a request whose `redirect` option was set to `manual`, and which was redirected by the server", with status 0 and empty headers. — [MDN, Response.type](https://developer.mozilla.org/en-US/docs/Web/API/Response/type)
- Safari 18.4: "Developers will need to add a `browser.permissions.request({origins: []})` call before doing any fetch() that is blocked by CORS." — cited in [safari_ios_deployment.md Q1](../Fitur%20deteksi%20situs%20phishing/safari_ios_deployment.md), from [WebKit, Safari 18.4 release notes](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)
- Cloaking evidence for why the phone's vantage point matters: server-side IP, UA and geo filters, and 2023–25 kits with client-side IP-reputation checks (412 clusters, 19,778 pages, 14 IP-intel APIs). — [Nahapetyan et al., arXiv 2509.13186 (2025)](https://arxiv.org/html/2509.13186v2); see also cloaking section in [html_headers_redirect.md Q4](../Fitur%20deteksi%20situs%20phishing/html_headers_redirect.md)

### Inferences
- **What Shoo gets.** `const r = await fetch(tab.url, {redirect:'follow', credentials:'omit', cache:'no-store'})` gives `r.status`, `r.redirected`, the final `r.url` (cross-host redirect if different), `Server`, `X-Powered-By`, CSP/HSTS presence and `Content-Type`. These are the header features in Shukla et al. (prior notes) for the exact path the user is on. They are computed on the phone, so nothing new leaves the device except the request to the site itself. `redirect:'manual'` only tells you "a redirect happened" (type `opaqueredirect`), never where it went.
- **Hop reconstruction.** Only possible step-by-step if the extension does not follow redirects, and Fetch hides `Location` from it. So a full hop chain is not possible on iOS. Combine `r.redirected` + final URL with the `webNavigation.onBeforeNavigate`/`onCommitted` sequence from the prior notes.
- **Cookies and credentials.** Use `credentials:'omit'`. Sending the user's cookies to a phishing origin could tie the probe to the victim's session, and there is no reason to authenticate. How Safari's ITP treats cookies on an extension background fetch is unknown (see Gaps).
- **Safety and ethics.** Re-fetching can trigger kit visitor logging. It can invalidate single-use links (`?token=`, victim-ID parameters used by campaign trackers) and double-count. Also, kits that show different content on a second visit or to non-JS clients will return decoy HTML. Recommendation: run the background probe only on pages already flagged "uncertain". Use `HEAD` or `GET` without credentials. Never probe URLs that contain the user's email or IDs in the query (check this on device).
- **App Review and privacy.** No new permission beyond host access, which Shoo already has. Safari 18.4+ needs the `permissions.request` step. No data goes to Shoo's server.

### Gaps
- Not verified on iOS whether Safari's background `fetch` exposes all headers (the Chromium exemption) or CORS-filters them even after `permissions.request`. Device test needed: fetch a cross-origin URL without `Access-Control-Allow-Origin` and read `r.headers.get('server')`.
- Unknown: the cookie and ITP behaviour, the User-Agent string, and whether iCloud Private Relay applies to Safari extension background fetches (it would change the "user's IP" assumption).
- No measurement found comparing cloaking rates for an on-device extension re-fetch vs. a datacenter fetch.

## Q4. Containing-app native options (Network Extension), with the iOS 26 URL Filter in depth

### Takeaway
For a consumer App Store app on an unsupervised iPhone, only three NE paths exist: the **URL Filter** (iOS 26+), a **packet tunnel** (iOS 9+, but Apple DTS says it is VPN-only and not for filtering or telemetry), and **DNS settings** (iOS 14+, configuration only, sees nothing). Content filters (`NEFilterDataProvider`) need a supervised device, the Screen Time path (child devices only), or per-app management. DNS proxy needs supervised or managed devices. The URL Filter fits Shoo's privacy model very well: the app never sees URLs, and the PIR/OHTTP backend never sees the URL or the user. But it is a **binary block-list enforcer**, not an observation channel. It gives no telemetry, no warn-and-continue, and no custom block page. It needs Apple approval plus a PIR server, a Privacy Pass issuer and an OHTTP gateway that Shoo would have to host. Expect several weeks of onboarding friction.

### Cited Findings
**Deployment matrix (Apple TN3134, current)**
- Packet tunnel: iOS 9.0 app extension, "per-app mode requires managed device". App proxy: iOS 9.0 "managed devices only". **URL filter provider: iOS 26.0, macOS 26.0, with no restriction listed.** Content filter: iOS 9.0 "supervised devices only". iOS 15.0 "apps using Screen Time APIs". iOS 16.0 "per-app on managed devices". DNS proxy: iOS 11.0 "supervised devices only". 16.0 "per-app on managed devices". Hotspot provider: iOS 26.0. — [Apple, TN3134 "Network Extension provider deployment"](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment)
- Screen Time path: "In the Screen Time case, content filters are only supported on child devices." It needs the Family Controls capability, a device "signed in as an under 18 child member of an iCloud family", `requestAuthorization(for: .child)` (iOS 16+), parent or guardian approval, and a separate distribution entitlement request. — [Apple, TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment)
- Forum reports match this. On an unsupervised iOS 18.6.2 device, saving an `NEFilterDataProvider` configuration fails with "Configuration invalid or read/write failed". DTS says individual (non-child) Family Controls enrolment does not enable content filters. — [Apple Developer Forums 815373](https://developer.apple.com/forums/thread/815373); [Forums 687333](https://developer.apple.com/forums/thread/687333)
- DNS proxy on a public App Store app: limited to supervised devices (system-wide) or managed devices (per-app). "the deployment mechanism is not the gating factor here, it's whether the device is supervised or not." — [Apple Developer Forums 795564](https://developer.apple.com/forums/thread/795564); [Forums 116144](https://developer.apple.com/forums/thread/116144)

**Packet tunnel (on-device "VPN" firewalls)**
- TN3120: "Do not use a packet tunnel provider to implement a network content filter." Packets are "not meant to be dropped or re-injected back into the system". Also: "Do not use a packet tunnel provider to intercept all DNS traffic on the system." It points to `NEFilterDataProvider`, DNS proxy, DNS settings, or, since 2025-07-22, the URL filter. — [Apple, TN3120 "Expected use cases for Network Extension packet tunnel providers" (rev. 2025-07-22)](https://developer.apple.com/documentation/technotes/tn3120-expected-use-cases-for-network-extension-packet-tunnel-providers)
- DTS (Quinn, Jun 2025): "DTS doesn't support folks using a packet tunnel provider as a content filter". The URL Filter has "fewer deployment restrictions". — [Apple Developer Forums 786284](https://developer.apple.com/forums/thread/786284)
- DTS (Quinn, Aug 2026), on pairing a URL Filter with a packet tunnel for blocked-URL statistics: "DTS certainly won't support this ... we only support you using a packet tunnel provider to implement VPN". The `packet-tunnel-provider` entitlement "is available to all paid developers". On getting blocked-URL details: only `reportEndpoint`, and "The fact that this only works on supervised devices is an important signal ... your overall goal is not compatible with Apple's privacy goals for general users." — [Apple Developer Forums 842671 (Aug 2026)](https://developer.apple.com/forums/thread/842671)
- WWDC25: "NEPacketTunnelProvider operates at the IP layer, and will not receive flow or application level metadata needed to do other things, like proxying DNS requests or content filtering." — [Apple, WWDC25 session 234 "Filter and tunnel network traffic with NetworkExtension" (2025)](https://developer.apple.com/videos/play/wwdc2025/234/)
- Memory: Apple does not document the limit. Developers report ~50 MiB on iOS 16 and ~15 MB again on iOS 17 (termination ~12 MB). DTS: do not hard-code limits, test across devices. — [Apple Developer Forums 106377](https://developer.apple.com/forums/thread/106377); [Forums 73148](https://developer.apple.com/forums/thread/73148); [Forums 728876](https://developer.apple.com/forums/thread/728876)
- App Review 5.4: VPN apps "must utilize the NEVPNManager API and may only be offered by developers enrolled as an organization". They must declare data collection before use, "may not sell, use, or disclose to third parties any data for any purpose". "Parental control, content blocking, and security apps, among others, from approved providers may also use the NEVPNManager API." — [Apple, App Store Review Guidelines §5.4 (current)](https://developer.apple.com/app-store/review/guidelines/)
- Practical examples. Lockdown Privacy is "an open source firewall that blocks trackers, ads, and badware in all apps" (GPL-3.0). Its repo bundles `Dnscryptproxy.xcframework` and a "Lockdown Tunnel" target, which suggests DNS-level blocking inside a local tunnel (inferred from file names). DNSCloak, 1.1.1.1 and NextDNS install a VPN configuration to intercept DNS. A commenter guessed `NEPacketTunnelProvider`, which is not confirmed. — [confirmedcode/Lockdown-iOS (GitHub)](https://github.com/confirmedcode/Lockdown-iOS); [Apple Developer Forums 656415](https://developer.apple.com/forums/thread/656415)
- An active VPN shows a status icon. Apple lists a VPN icon among iPhone status icons, and users report it appears in Control Center. — [Apple Support, "Learn the meaning of the iPhone status icons"](https://support.apple.com/en-asia/guide/iphone/iphef7bb57dc/ios)

**DNS settings (encrypted DNS)**
- `NEDNSSettingsManager` creates a DoH/DoT configuration. "In order to use your DNS settings, the user needs to enable it in the Settings app on iOS". — [Apple, NEDNSSettingsManager](https://developer.apple.com/documentation/networkextension/nednssettingsmanager)

**URL Filter (iOS 26+): architecture**
- "Network Extension URL Filter allows you to filter system-wide HTTP and HTTPS requests, matching against the full URL of the request." It is "system-wide. Checking all HTTP requests sent via Apple networking APIs, such as WebKit and URLSession". Other stacks must call `NEURLFilter.verdict(for:)` voluntarily. — [WWDC25 session 234](https://developer.apple.com/videos/play/wwdc2025/234/); [Apple, "URL filters"](https://developer.apple.com/documentation/networkextension/url-filters)
- "Your app does not execute in the filtering path and has no access to traffic." "the URL contents are not revealed to the app, and all database queries to the backend servers are anonymized". "The entire chain of backend servers, both Apple's and your servers, will have no access to any of the content and identity information." — [WWDC25 session 234](https://developer.apple.com/videos/play/wwdc2025/234/)
- Flow: an on-device Bloom prefilter (fetched by your `NEURLFilterControlProvider`). Negative means allow immediately. Positive means a homomorphic-encryption PIR lookup to your PIR server, keyed by URL with value 1. Requests are authenticated with Privacy Pass tokens from your issuer, after device attestation. They go through an Apple-run OHTTP relay to your OHTTP gateway. A match means deny. — [WWDC25 session 234](https://developer.apple.com/videos/play/wwdc2025/234/); [Apple, "Filtering traffic by URL" sample (iOS 26)](https://developer.apple.com/documentation/networkextension/filtering-traffic-by-url)
- Matching: the system Punycodes the URL. It then generates sub-URLs: each host suffix (e.g. `example.com`, `sub1.example.com`), with and without `:443`, each path prefix with and without trailing `/`, and with or without query and fragment. Each sub-URL is checked against the Bloom filter, then PIR. "Neither the Bloom filter nor PIR supports wildcards or regular expressions". `urlParsingConfiguration` (exclude domain, path, query or fragment, replaced with `%*`) and `urlParsingRegularExpression` (case-insensitive custom parsing) are **iOS 27.0**. — [Apple, NEURLFilterManager](https://developer.apple.com/documentation/networkextension/neurlfiltermanager); [urlParsingConfiguration](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/urlparsingconfiguration); [urlParsingRegularExpression](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/urlparsingregularexpression)
- Parameters: `prefilterFetchInterval` defaults to 86400 s with a minimum of 2700 s (45 min). `shouldFailClosed` defaults to `false`, meaning that on a PIR or communication failure "URLs are allowed". Info.plist needs an `NSPIRConfiguration` dict (`PIRServerURL`, optional `PrivacyPassIssuerURL`). — [prefilterFetchInterval](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/prefilterfetchinterval); [shouldFailClosed](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/shouldfailclosed); [NEURLFilterManager](https://developer.apple.com/documentation/networkextension/neurlfiltermanager)
- Reporting (iOS 27): `reportEndpoint`, `reportFormat` and `reportInterval` (default 1 day, minimum 1 h) send blocked-URL lists over the same OHTTP relay. "Reporting is available only on supervised devices." — [reportEndpoint](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/reportendpoint); [reportInterval](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/reportinterval)
- Entitlement and approval: "Add the new Network Extension url-filter-provider entitlement". "This is a capability that you must apply for ... Apple will validate your server configuration for Oblivious HTTP Relay before approval." That is required for App Store, TestFlight, ad-hoc, Developer ID and enterprise builds. Development-signed builds are exempt. It works "on both managed and unmanaged devices". MDM URL Filter configuration requires supervision. Registration goes through CloudKit Console → Identity & Trust. — [WWDC25 session 234](https://developer.apple.com/videos/play/wwdc2025/234/); [Apple, "URL filters"](https://developer.apple.com/documentation/networkextension/url-filters)
- PIR server: Apple ships a sample PIR server as a Dockerfile, run with Apple's `container` tool on macOS 26 or any PaaS. Its `usecase` name must equal the extension bundle ID + `.url.filtering`, and `BloomFilterTool` builds both the prefilter and `input.txtpb`. — [Apple, "Setting up a PIR server for URL filtering"](https://developer.apple.com/documentation/networkextension/setting-up-a-pir-server-for-url-filtering)
- Field reports. A scam-blocker app (`app.scamzero`, ~37k-domain prefilter) with approved URL-Filter entitlements loops on iOS 26: Apple's relay returns 404 for its Privacy Pass issuer directory. DTS (Sep 2026) says there are two PIR states, "Approved" (not yet configured) and "Successfully Onboarded". — [Apple Developer Forums 843796 (Sep 2026)](https://developer.apple.com/forums/thread/843796). Other reports: production builds fail with `serverSetupIncomplete` (9) because no privacy proxy was provisioned. A blocked page in Safari shows a generic "couldn't load any data" error with no custom page. Opening the same URL from WhatsApp loaded it, which DTS called a bug (Sep 2025). — [Forums 802425](https://developer.apple.com/forums/thread/802425); [Forums 815702](https://developer.apple.com/forums/thread/815702)
- Critique by a browser-security engineer. Only binary verdicts ("no way ... 'Warn and allow override'"). No way to submit extra context such as redirects or IPs. No false-positive feedback path. A 45-minute minimum prefilter update. Lookups cannot discover new URLs. The privacy trade-offs are "baked" in with no overrides. — [Eric Lawrence, "First Look: Apple's NEURLFilter API", text/plain blog (10 Jun 2025)](https://textslashplain.com/2025/06/10/apple-url-filter-api/)

### Inferences
- **What each native option can see, and its cost for Shoo.**

| Method | iOS | Consumer App Store, unsupervised? | Sees | What leaves phone | App Review / UX risk |
|---|---|---|---|---|---|
| URL Filter (`NEURLFilterManager`) | 26+ (parsing options 27+) | Yes, after Apple approval of `url-filter-provider` + PIR onboarding | Nothing (the system matches; the app is blind). Full-URL sub-URL matching against Shoo's list | Encrypted PIR queries via Apple OHTTP relay → Shoo's OHTTP gateway/PIR (server sees neither URL nor IP). Only on Bloom hits | Low review risk (Apple-sanctioned). Generic Safari error page. Binary block. Fail-open by default |
| Packet tunnel (local "VPN") | 9+ | Technically yes (entitlement open to paid devs). DTS-unsupported for filtering. §5.4 needs org enrolment | IP packets: DNS queries (if DNS routed to the tunnel), destination IPs, TLS ClientHello SNI (unless ECH), never full HTTPS URLs or headers | Nothing, if processed locally | High: off-label use, VPN icon, conflicts with real VPNs, 15–50 MB memory, battery. §5.4 "may not ... use ... any data for any purpose" |
| DNS settings (`NEDNSSettingsManager`) | 14+ | Yes. The user must enable it in Settings | Nothing on device. Shoo's resolver would see every hostname from every app | Every DNS query to Shoo's resolver | Breaks Shoo's "registrable domain only on report" rule. Big privacy-policy burden |
| DNS proxy (`NEDNSProxyProvider`) | 11+ | **No** (supervised/managed only) | All DNS queries | — | Not available |
| Content filter (`NEFilterDataProvider`) | 9+ / 15+ Screen Time / 16+ per-app | **No**, except child devices via Family Controls | Flows: host/SNI, IP, app, first bytes (HTTPS still encrypted) | — | Not available for adult users |

- **Is the URL Filter a fit?** Yes, for *enforcement of Shoo's own blocklist*: confirmed-scam URLs from user reports, the Worker's layer 3–4 verdicts, and Indonesian scam feeds. It covers Safari *and* every WebKit/URLSession app (in-app browsers in WhatsApp/Telegram/Instagram if they use WKWebView), which the Safari extension cannot reach. Its privacy model is stronger than Shoo's current "send eTLD+1" rule, so Shoo could even stop sending domains for list checks. It is **not** an observation method. It gives no runtime or network features, and Shoo cannot learn which URLs were blocked (reports are supervised-only). So it complements the extension. It does not replace webRequest.
- **URL Filter costs for a student team.** (1) Apple approval and onboarding. The field reports show multi-week "Approved but not onboarded" states. (2) Three services to host: a PIR server (Swift sample, containerised — not runnable on Cloudflare Workers, which do not run Swift containers; it would need Cloudflare Containers, Fly or a VPS), a Privacy Pass issuer, and an OHTTP gateway. (3) Bloom updates are at most every 45 min, so fresh campaigns (median uptime ~24 h, per the prior notes) partly escape. Feed the extension's DNR dynamic rules for minute-level freshness. (4) Binary block and a generic error page conflict with Shoo's warn-then-continue UX. Keep the URL Filter for high-confidence "block" verdicts only and the extension for warnings. (5) Set `shouldFailClosed=false` (default) to avoid breaking browsing on outages. (6) Watch the WhatsApp-to-Safari bypass bug.
- **Packet tunnel is not recommended.** DTS explicitly does not support filtering or telemetry use. It forces a persistent VPN icon and kills compatibility with users' real VPNs. It only sees DNS/SNI/IP, which Shoo can already approximate via the eTLD+1 it has in the extension. §5.4 also requires the developer account to be an organization.
- **The containing app adds nothing for page-level observation.** The Safari extension's native handler (`SFSafariExtensionHandler`/`NSExtensionRequestHandling`) gets only what the JS side sends it. No NE provider available to consumer apps exposes Safari's HTTP headers, status codes or redirect hops.

### Gaps
- Whether URL Filter checks Safari **subresource** requests (`fetch` to an exfil endpoint) as well as top-level navigations. "All URL requests via WebKit" implies yes, but I found no explicit test. If yes, Shoo could block known kit exfil endpoints system-wide.
- Whether URL Filter can coexist with another vendor's URL Filter or content filter (single-slot limit?). Not documented in the sources read.
- Whether Safari on iOS 26 uses ECH by default (which would hide SNI from any packet tunnel). Not researched.
- Exact current packet-tunnel memory limit on iOS 26/27. Apple does not publish it.
- App Review's stance on a Safari-extension security app also shipping a packet tunnel. DTS declined to comment ("I don't work for App Review").

## Q5. Academic evidence on runtime-behaviour and network features for phishing detection

### Takeaway
Runtime JS and network features are well proven for **clustering kits and defeating cloaking in crawlers**: API-set clustering FMI 0.98, CrawlPhish cloaking detection FPR 1.45%, and network-timing detection of MITM kits at 99.9% accuracy. They are also proven for **encrypted-traffic classification** (~95% accuracy from TLS features). I found **no peer-reviewed study that measures the accuracy or FPR of runtime-hook or exfil-endpoint features collected inside real users' browsers**. Treat their marginal gain over Shoo's URL+DOM+LLM stack as unmeasured. The strongest-evidence cheap runtime signals are exfil to messaging APIs, brand-resource hotlinking, and API-capability fingerprints (fingerprinting, IP checks, `atob`/`eval` obfuscation).

### Cited Findings
- **Nahapetyan et al. (2025, arXiv, open).** VisibleV8-instrumented Chromium on 1,328,917 pages (Aug 2023–Jan 2025), with 4,180 recovered kits. Clustering by executed browser-API sets reaches 98% accuracy (FMI 0.98, or 0.73 on a rebalanced set; V-measure 0.92). Script hashes reach only 0.71–0.85. Technique-to-API map: client-side IP check is `fetch`/`XMLHttpRequest.open`, timing bot detection is `Performance.now` + timeout, and encoding is `atob`/`TextDecoder.decode`. Prevalence figures are in Q1. — [arXiv 2509.13186, DOI 10.48550/arXiv.2509.13186](https://arxiv.org/html/2509.13186v2)
- **Favoretti, Dantas & Pereira Jr. (SBSeg 2025, open).** A modified Chromium collects data from 432,237 evasive phishing samples over 8 months, despite client- and server-side cloaking. Clustering by deployment characteristics reaches NMI 0.846. — ["Inside the Phishing Reel: Leveraging Browser Instrumentation to Analyse Evasive Phishing", Anais do SBSeg 2025, DOI 10.5753/sbseg.2025.11391](https://sol.sbc.org.br/index.php/sbseg/article/download/36642/36429)
- **CrawlPhish (IEEE S&P 2021, paywalled).** Detects client-side JS cloaking with FPR 1.45% and FNR 1.75%. Cloaking use grew from 23.32% to 33.70%. — [Zhang et al., DOI 10.1109/SP40001.2021.00021](https://doi.org/10.1109/SP40001.2021.00021) (open PDF: [kapravelos.com/publications/crawlphish-sp21.pdf](https://kapravelos.com/publications/crawlphish-sp21.pdf)) [older, 2021]
- **Catching Transparent Phish (ACM CCS 2021, ACM-paywalled, open copy on NSF PAR).** Network-level properties (timing and TLS) of MITM reverse-proxy kits (Evilginx, Muraena, Modlishka). The PHOCA classifier reaches 99.9% accuracy. 1,220 MITM phishing sites were found, and only 43.7% of their domains and 18.9% of their IPs were on blocklists. — [Kondracki, Azad, Starov & Nikiforakis, DOI 10.1145/3460120.3484765](https://doi.org/10.1145/3460120.3484765); [open PDF, NSF PAR](https://par.nsf.gov/servlets/purl/10337720) [older, 2021]
- **TLS-traffic phishing detection (Cluster Computing 2023, Springer, paywalled).** Features from TLS 1.2/1.3 traffic without decryption. RF 93.6%, XGBoost 95.07%, LightGBM 95.40% accuracy. — [Kumar, Kondaiah, Pais & Rao, "Machine learning models for phishing detection from TLS traffic", DOI 10.1007/s10586-023-04042-6](https://doi.org/10.1007/s10586-023-04042-6)
- **Encrypted malicious-traffic ensemble (J. Network & Systems Management 2024, Springer, paywalled).** TLS features across phishing, legitimate and malware sites. Ensemble ~94.9%, deep ensemble ~96.7% accuracy (search-snippet figures; verify in the full text). — [DOI 10.1007/s10922-024-09847-3](https://doi.org/10.1007/s10922-024-09847-3)
- **Sunrise to Sunset (USENIX Security 2020, open).** Brand-resource loads from phishing pages (with Referer) reveal phishing pages and victims at scale. Other figures are in Q2. — [Oest et al.](https://www.usenix.org/conference/usenixsecurity20/presentation/oest-sunrise) [older, 2020]
- **Leaky Forms (USENIX Security 2022, open).** Method reference for exfiltration monitoring: the crawler fills email/password fields, monitors network traffic, and intercepts script access to inputs. Emails went to third parties before submission on 1,844 (EU) and 2,950 (US) of the top-100k sites. Passwords were collected on 52 sites by session-replay scripts. Not phishing, but it shows that *benign* sites also send typed data off-site before submit, which is an FP risk for an "early exfil" rule. — [Senol, Acar, Humbert & Borgesius](https://www.usenix.org/conference/usenixsecurity22/presentation/senol); [code](https://github.com/asumansenol/leaky-forms)
- **Client-side request graphs (method evidence, ad/tracker domain).** AdGraph builds a graph from DOM + network + JS, and replicates filter-list labels with 95.33% accuracy on the Alexa top-10K. — [Iqbal et al., IEEE S&P 2020, DOI 10.1109/SP40000.2020.00005 (open)](https://doi.org/10.1109/SP40000.2020.00005). Function-level attribution of tracking JS reaches 94% precision and 98% recall, robust to off-the-shelf obfuscation. — ["Blocking Tracking JavaScript at the Function Granularity", ACM CCS 2024, DOI 10.1145/3658644.3670329 (open)](https://doi.org/10.1145/3658644.3670329); see also AdCPG, [ACM CCS 2023, DOI 10.1145/3576915.3623084](https://doi.org/10.1145/3576915.3623084)
- **Static and graph resource features (for comparison).** A hyperlink web-graph classifier (C4.5) reaches 97.8% accuracy. — [Computers & Security (Elsevier, paywalled), PII S016740482030078X](https://www.sciencedirect.com/science/article/abs/pii/S016740482030078X) [older, 2020]. Seven external-service features alone reach 94.09% accuracy. — [arXiv 2010.12847 (open)](https://arxiv.org/pdf/2010.12847) [older, 2020]
- **Vendor practice.** Joe Security added generic JS instrumentation that can trace any API call with full parameters to its phishing sandbox. This is a vendor claim with no evaluation. — [Joe Security blog (2023)](https://www.joesecurity.org/blog/7492960968739667986)

### Inferences
- **Evidence ranking for Shoo's on-device runtime features.** (1) Exfil destination is a messaging or bot API, or an off-site host with a credential-like body shortly after password/OTP input. This is backed by kit studies (Telegram dominance, prior notes) but has no measured FPR. Leaky Forms shows benign third-party pre-submit leaks exist, so require the destination to be a messaging/bot API or a newly-seen eTLD+1, not a known tracker. (2) Brand resources loaded from a non-brand page (Oest et al.), easy via Resource Timing. (3) API-capability set: fingerprinting, client-side IP-intel calls, `atob`/`eval`/`SubtleCrypto.decrypt`, Turnstile or fake CAPTCHA. These are strong for kit clustering (FMI 0.98), weaker as a benign/phish separator, because benign sites also fingerprint.
- **Network-level (DNS/SNI/TLS) features** reach ~95% in lab TLS datasets. Shoo cannot collect them on iOS without an off-label packet tunnel, and the eTLD+1 already carries most of that domain signal. Low value for the cost.
- **MITM kits (Evilginx-style) defeat DOM- and visual-based detection**, because the content is the real brand page. Network-timing detection (PHOCA) is server- or crawler-side. On device, the cheap tell is a brand-perfect DOM on a non-brand eTLD+1. Shoo's existing brand-vs-domain check covers this.
- **Paywalled DOIs to fetch via MyLoft:** 10.1109/SP40001.2021.00021 (IEEE), 10.1145/3460120.3484765 (ACM; open copy exists), 10.1145/3555050.3569131 (ACM; arXiv copy exists), 10.1007/s10586-023-04042-6 (Springer), 10.1007/s10922-024-09847-3 (Springer), and the Computers & Security graph paper (Elsevier, PII S016740482030078X).

### Gaps
- No peer-reviewed measurement of a phishing detector that uses **in-browser extension hooks or Resource Timing from real users**, so no accuracy, FPR or latency numbers for Shoo's exact setting.
- No 2023–2026 DNS-only phishing-detection paper with solid numbers turned up in my searches.
- The full texts of the two Springer TLS papers were not read (paywalled). Their dataset sizes and FPR are unverified.
- No Indonesia-specific study of exfil channels (WhatsApp/Telegram bot APIs) in kits.
