# Shoo membaca DOM, bukan lalu lintas jaringan

Di iPhone, Shoo bisa membaca dan mengubah DOM halaman hampir tanpa batas. Sebaliknya, Shoo **tidak bisa** mengamati lalu lintas jaringan halaman secara utuh. Content script (iOS 15+), injeksi `world: MAIN` (iOS 16.4+ lewat `scripting.registerContentScripts`, iOS 18+ lewat manifest), `match_about_blank` (iOS 18.4+), dan pembacaan closed shadow DOM (Safari 26) memberi akses penuh ke struktur halaman yang dilihat korban. Untuk jaringan, Apple menulis "`webRequest`: Not supported in iOS". Jadi header respons, kode status, hop redirect 3xx, DNS, dan SNI dari pemuatan halaman tidak terbaca oleh ekstensi. Aplikasi induk juga tidak menutup celah itu: satu-satunya jalur Network Extension yang sah untuk pengguna dewasa di App Store adalah **URL Filter iOS 26**, dan URL Filter hanya memblokir tanpa melihat apa pun. Ada tiga jendela sempit ke lalu lintas halaman: hook `fetch`/XHR di MAIN world (tujuan request terlihat sebelum terkirim, perlu izin `scripting`), Resource Timing (URL dan `initiatorType` setiap resource tanpa izin baru, tetapi Safari tidak punya `responseStatus`), dan refetch dari background (status dan URL akhir, bukan rantai hop). Belum ada studi peer-reviewed yang mengukur akurasi sinyal runtime atau jaringan yang dikumpulkan di browser pengguna sungguhan. Kasus nyata yang lolos, klon login Microsoft di `helpnets.info`, menunjukkan prioritasnya. Halaman itu mengembalikan HTTP 200 tanpa redirect di belakang Cloudflare, jadi sinyal jaringan tidak akan membantu. Semua bukti justru ada di DOM, dan sebagian besar **sudah ada di PageSnapshot yang dikirim hari ini**: `loginfmt`, `i0116`, `i0118`, `passwd`, `idSIButton9`, dan alt "Microsoft". Satu aturan sidik jari kit Microsoft, ditambah klaim merek dari favicon, akan menaikkan skor dari 15 ke rentang warning atau block tanpa mengumpulkan data baru.

## Content script membaca dan mengubah DOM sejak iOS 15

Hampir semua kemampuan inspeksi DOM sudah tersedia di Safari iOS dan sudah lama stabil. Content script didukung sejak **iOS 15**, termasuk `all_frames` dan `exclude_matches`. `world` (MAIN/ISOLATED) di manifest tersedia sejak iOS 18, dan `match_about_blank` serta `match_origin_as_fallback` sejak iOS 18.4 ([MDN BCD content_scripts](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/content_scripts.json)). Jalur programatik datang lebih awal. `scripting.executeScript` dengan `world: MAIN` tersedia sejak iOS 15.4, dan `registerContentScripts` dengan `RegisteredContentScript.world` sejak **iOS 16.4** ([MDN BCD scripting](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/scripting.json)). Seorang engineer Apple mengonfirmasi bahwa "Safari 16.4 does support "MAIN" for registerContentScripts" ([Apple Developer Forums 728849](https://developer.apple.com/forums/thread/728849)). Safari 26 menambahkan `dom.openOrClosedShadowRoot()`, sehingga kit yang menyembunyikan form di closed shadow root tetap terbaca ([WebKit, Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)).

Manipulasi DOM sudah dipakai Shoo: mencoret field sensitif, mem-blur screenshot, dan menyorot evidence (EX-05). Kemampuan ini tidak butuh izin baru, karena Shoo sudah memegang akses host ke semua situs http(s). Untuk membaca dan mengubah DOM di ISOLATED world, biaya App Review dan label privasinya nol. Ada dua batas praktis yang perlu diingat. Pertama, catatan BCD menyebut content script "are not applied to tabs until the user grants permission via the extension's access alert". Pemuatan pertama setelah izin diberikan karena itu bisa tidak mengikuti `run_at` ([MDN BCD content_scripts](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/content_scripts.json)). Kedua, `webNavigation.onHistoryStateUpdated` tidak didukung di iOS, sehingga perubahan URL di SPA harus dideteksi dari content script lewat `popstate` atau polling ([Apple, Assessing your Safari web extension's browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)). Di repo, `snapshot.js` saat ini membaca form di iframe same-origin dari top frame. Iframe lintas origin masih dilewati (komentar "Phase 2"). Jika iframe itu perlu dibaca, `all_frames` dan `match_about_blank` adalah jalurnya.

Alasan terkuat untuk memusatkan deteksi di DOM perangkat tetap cloaking. CrawlPhish menemukan **31,3%** dari 112.005 situs phishing memakai cloaking sisi klien. Konten di balik gerbang mouse-detection dan click-through tetap dilihat oleh 100% dan 97,72% pengguna ([CrawlPhish, IEEE S&P 2021](https://kapravelos.com/publications/crawlphish-sp21.pdf)). Situs dengan filter sisi server hanya masuk blocklist **23,0%** dibanding 49,4% untuk situs tanpa filter ([PhishFarm, IEEE S&P 2019](https://adamdoupe.com/publications/phishfarm-oakland2019.pdf)). Content script Shoo membaca halaman di Safari asli, dengan IP seluler dan setelah gerbang dilewati, persis seperti yang dilihat korban.

## Header, status, dan hop redirect tetap gelap di iPhone

Konflik dokumentasi `webRequest` belum selesai, dan sikap yang aman adalah menganggap API itu tidak ada. Data MDN menyebut `webRequest` tersedia di Safari iOS 18, lengkap dengan `onBeforeRedirect` yang membawa `redirectUrl`, `statusCode`, dan `responseHeaders` ([MDN BCD webRequest](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/webRequest.json)). Halaman resmi Apple menulis "`webRequest`: Not supported in iOS" dan "`opt_extraInfoSpec` not supported for any of the events" ([Apple, Assessing… compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)). Apple juga menyarankan background persisten **di macOS** untuk `webRequest`, karena callback "might fail if Safari unloads the background page". Padahal di iOS background wajib non-persisten ([Apple, Optimizing your web extension for Safari](https://developer.apple.com/documentation/safariservices/optimizing-your-web-extension-for-safari)).

Jalur pengganti di dalam halaman juga buta terhadap lintas origin. `PerformanceNavigationTiming.redirectCount` (iOS 15.1) bernilai "`0` if the redirect is cross-origin" ([MDN redirectCount](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming/redirectCount)), padahal hop phishing hampir selalu lintas origin. `webNavigation` dasar (`onBeforeNavigate`, `onCommitted`, `onCompleted`, `onErrorOccurred`) tersedia sejak iOS 15. API ini bisa merekam urutan navigasi satu tab, termasuk redirect JS dan meta-refresh, tetapi tidak melihat hop 3xx dan tidak punya `transitionType` ([MDN BCD webNavigation](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/webNavigation.json)). `declarativeNetRequest` bisa memblokir dan me-redirect sejak iOS 15/15.4, tetapi tidak membaca respons, dan `onRuleMatchedDebug` tidak didukung ([MDN BCD declarativeNetRequest](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/declarativeNetRequest.json)).

DNS dan SNI sama sekali di luar jangkauan ekstensi. Fitur DNS hanya bisa dihitung di server dari eTLD+1, misalnya lewat DoH dari Worker. IP Cloudflare, AWS, dan Google tidak membawa informasi, karena situs legit dan phishing sama-sama memakainya. Kekuatan buktinya juga terbatas. Satu paper fitur header melaporkan akurasi 97,8% dari satu dataset ([Shukla et al., ETT 2024](https://onlinelibrary.wiley.com/doi/abs/10.1002/ett.4872)), dan catatan riset tidak menemukan studi peer-reviewed 2019–2026 yang mengukur fitur rantai redirect. Jadi Shoo kehilangan sinyal yang buktinya memang paling tipis.

## Tiga jendela sempit ke lalu lintas halaman

### Hook MAIN world melihat tujuan, bukan isi

Hook di MAIN world adalah satu-satunya cara di dalam browser untuk melihat ke mana JavaScript halaman mengirim data. Background memanggil `browser.scripting.registerContentScripts([{ world:'MAIN', runAt:'document_start', allFrames:true, matches:['http://*/*','https://*/*'] }])`. Hook lalu membungkus `fetch`, `XMLHttpRequest.prototype.open`/`send`, `navigator.sendBeacon`, konstruktor `WebSocket`, `HTMLFormElement.prototype.submit`/`requestSubmit`, dan setter `src` gambar. Semua pembungkus ini berjalan sebelum request keluar, sehingga tujuan selalu terlihat, termasuk untuk request `no-cors` yang responsnya opaque. Respons yang diterima hook sama dengan yang diterima halaman. Untuk same-origin, semua header kecuali `Set-Cookie` terbaca. Untuk CORS, hanya header safelisted. Untuk `opaque`, "`status` property is set to `0`, `body` is `null`, headers are empty" ([MDN, Response.type](https://developer.mozilla.org/en-US/docs/Web/API/Response/type)). Biayanya adalah izin `scripting`, yang belum ada di manifest Shoo. Izin ini tidak menambah prompt akses situs, tetapi mengubah daftar izin, sehingga label privasi App Store dan catatan review perlu diperbarui. Memakai key `world` di manifest akan menaikkan batas minimum ke iOS 18.

Kelemahannya struktural, dan keputusan desain harus mengikutinya. Hook mudah dideteksi. OpenWPM, crawler riset yang memakai teknik serupa, terdeteksi di **~14%** dari 100 ribu halaman depan, dan instrumentasinya bisa dirusak oleh halaman ([Krumnow et al., CoNEXT 2022](https://arxiv.org/abs/2205.08890)). Kit phishing 2023–2025 sudah melakukan fingerprinting dasar di 80% klaster dan cek timing di 22% ([Nahapetyan et al., arXiv 2509.13186](https://arxiv.org/html/2509.13186v2)). Hook juga tidak melihat request dari Worker, request sebelum hook terpasang, atau built-in dari iframe segar. Pesan dari MAIN world bisa dipalsukan oleh halaman. Chrome menyebut dua dunia hanya berbagi DOM dan memperingatkan bahwa content script "can create vulnerabilities" ([Chrome for Developers, Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)). Konsekuensinya, hook hanya boleh menambah risiko. Event dengan skema tetap divalidasi di ISOLATED world, dan "tidak ada eksfiltrasi terlihat" tidak boleh pernah dipakai untuk meloloskan halaman. Untuk privasi, hook tidak boleh membaca body, nilai form, header, atau cookie. Yang dipancarkan hanya jenis API, eTLD+1 tujuan (dihitung di perangkat), dan flag seperti `offsite` atau `known_exfil_service` (`api.telegram.org`, `discord.com/api/webhooks`). Bisa juga ditambah fakta waktu: "request terkirim < 2 detik setelah event `input` di field password". Fakta itu memakai event, bukan nilai yang diketik, jadi tetap patuh aturan "never collect typed values". Satu catatan FP penting: Leaky Forms menemukan email terkirim ke pihak ketiga **sebelum submit** di 1.844 (EU) dan 2.950 (US) situs top-100k ([Senol et al., USENIX Security 2022](https://www.usenix.org/conference/usenixsecurity22/presentation/senol)). Aturan "eksfiltrasi dini" karena itu harus dibatasi pada tujuan messaging/bot API atau eTLD+1 yang tidak dikenal, bukan tracker umum.

### Resource Timing gratis tetapi tanpa status

Resource Timing memberi daftar pasif semua yang dimuat halaman, tanpa izin dan tanpa bisa dibungkus balik oleh halaman. Di Safari iOS, `PerformanceResourceTiming`, `initiatorType`, dan `nextHopProtocol` tersedia sejak iOS 11, serta `transferSize` dan ukuran body sejak iOS 16.4. Namun **`responseStatus`, `contentType`, dan `contentEncoding` tidak didukung Safari sama sekali**, dan `worker_support` bernilai false di iOS ([MDN BCD PerformanceResourceTiming](https://github.com/mdn/browser-compat-data/blob/main/api/PerformanceResourceTiming.json)). Tanpa `Timing-Allow-Origin`, field timing dan `nextHopProtocol` bernilai nol atau string kosong. Request yang gagal karena CSP/CORS/mixed content tidak dicatat sama sekali ([W3C Resource Timing](https://w3c.github.io/resource-timing/)). Yang tersisa tetap berguna: URL lengkap setiap resource (`name`) dan `initiatorType`. Dari keduanya Shoo bisa menghitung himpunan eTLD+1 resource, mendeteksi resource yang dimuat dari domain merek padahal halaman bukan milik merek itu, dan mendeteksi request `fetch`/`xmlhttprequest`/`beacon` ke host lain setelah field kredensial muncul. Sinyal brand-hotlink punya dasar empiris. Golden Hour memakai beban resource merek dari halaman phishing untuk mengukur **4,8 juta** kunjungan korban ([Oest et al., USENIX Security 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/oest-sunrise)). Field `name` bisa berisi token atau email, jadi harus diringkas ke eTLD+1 di perangkat.

### Refetch dari background memberi status, bukan rantai

Background dengan akses host bisa me-`fetch` ulang URL tab untuk membaca `status`, semua header kecuali `Set-Cookie`, `response.redirected`, dan `response.url` akhir ([Chrome for Developers, Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)). Di Safari 18.4+, panggilan `browser.permissions.request({origins: []})` diperlukan sebelum fetch yang terblokir CORS ([WebKit, Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)). Rantai hop tetap tidak bisa direkonstruksi, karena `redirect:'manual'` menghasilkan `opaqueredirect` dengan status 0 tanpa `Location` ([MDN, Response.type](https://developer.mozilla.org/en-US/docs/Web/API/Response/type)). Refetch juga punya biaya etis. Ia mengirim request kedua ke server penyerang, yang bisa mengonfirmasi korban aktif atau membakar tautan sekali pakai. Kit yang menyajikan umpan ke klien tanpa JS juga akan mengembalikan HTML palsu. Refetch karena itu hanya pantas untuk halaman berstatus "tidak pasti", dengan `credentials:'omit'`, dan tidak pernah untuk URL yang memuat email atau ID pengguna di query. Belum terverifikasi apakah Safari iOS benar-benar membebaskan background fetch dari filter header CORS seperti Chromium.

| Metode | iOS minimum | Izin baru | Yang terlihat | Tidak terlihat | Biaya privasi / App Review |
|---|---|---|---|---|---|
| Content script ISOLATED (DOM) | 15 | Tidak ada | Seluruh DOM, form, atribut, `src`/`href`, script inline | Body script lintas origin, nilai jaringan | Nol bila diolah di perangkat |
| `world: MAIN` hook | 16.4 (`registerContentScripts`), 18 (manifest) | `scripting` | Tujuan, method, jenis body setiap `fetch`/XHR/beacon/WebSocket | Request Worker, request sebelum hook, header lintas origin | Sedang; perbarui label privasi dan review notes |

| Refetch background | 15; 18.4 perlu `permissions.request` | Tidak ada | Status, header, URL akhir | Hop perantara, isi setelah JS | Request kedua ke penyerang |

## Aplikasi induk hanya bisa memblokir, bukan mengamati

Untuk aplikasi App Store konsumen di iPhone yang tidak supervised, Apple TN3134 hanya menyisakan tiga jalur Network Extension. **URL Filter** (iOS 26) tidak punya pembatasan deployment. Packet tunnel (iOS 9) secara teknis tersedia. DNS settings (iOS 14) hanya berupa konfigurasi. Content filter (`NEFilterDataProvider`) butuh perangkat supervised, jalur Screen Time untuk perangkat anak, atau per-app di perangkat managed. DNS proxy butuh perangkat supervised atau managed ([Apple, TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment)). Packet tunnel tidak bisa dipakai untuk observasi secara sah. TN3120 menulis "Do not use a packet tunnel provider to implement a network content filter" ([Apple, TN3120](https://developer.apple.com/documentation/technotes/tn3120-expected-use-cases-for-network-extension-packet-tunnel-providers)). DTS menegaskan pada Agustus 2026 bahwa "we only support you using a packet tunnel provider to implement VPN" ([Apple Developer Forums 842671](https://developer.apple.com/forums/thread/842671)). App Review §5.4 juga mensyaratkan akun organisasi untuk aplikasi VPN dan melarang aplikasi itu "use ... any data for any purpose" ([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). DNS settings membuat resolver milik Shoo melihat setiap hostname dari setiap aplikasi, jadi langsung melanggar aturan privasi Shoo.

URL Filter cocok dengan model privasi Shoo, tetapi fungsinya penegakan, bukan pengamatan. Apple menyebut "Your app does not execute in the filtering path and has no access to traffic". Lookup berjalan lewat Bloom prefilter di perangkat, lalu PIR homomorfik melalui relay OHTTP Apple ke server PIR milik developer ([WWDC25 session 234](https://developer.apple.com/videos/play/wwdc2025/234/)). Biayanya nyata: entitlement `url-filter-provider` harus diajukan, Apple memvalidasi konfigurasi OHTTP, Shoo harus meng-host server PIR, issuer Privacy Pass, dan gateway OHTTP, dan prefilter diperbarui paling cepat tiap 45 menit ([NEURLFilterManager](https://developer.apple.com/documentation/networkextension/neurlfiltermanager); [prefilterFetchInterval](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/prefilterfetchinterval)). Reporting URL yang diblokir hanya tersedia di perangkat supervised ([reportEndpoint](https://developer.apple.com/documentation/networkextension/neurlfiltermanager/reportendpoint)). Vonisnya biner, tanpa opsi "warn and allow override" dan tanpa halaman blokir kustom ([Eric Lawrence, First Look: Apple's NEURLFilter API](https://textslashplain.com/2025/06/10/apple-url-filter-api/)). Laporan lapangan juga menunjukkan aplikasi scam-blocker yang entitlement-nya sudah disetujui bisa tertahan di status "Approved" tetapi belum "Successfully Onboarded" ([Apple Developer Forums 843796](https://developer.apple.com/forums/thread/843796)). Kesimpulannya, URL Filter layak sebagai tahap lanjut untuk memblokir domain berkeyakinan tinggi di Safari dan in-app browser WebKit, bukan sebagai sumber fitur deteksi.

## Bukti akurasi kuat untuk crawler, kosong untuk browser pengguna

Sinyal runtime dan jaringan terbukti kuat di lingkungan crawler dan lab. Bukti di browser pengguna nyata belum ada. Pengklasteran kit berdasarkan himpunan browser API mencapai Fowlkes-Mallows **0,98**, sedangkan hash SHA-256 script hanya 0,71–0,85 ([Nahapetyan et al.](https://arxiv.org/html/2509.13186v2)). CrawlPhish mendeteksi cloaking JS dengan FPR 1,45% ([CrawlPhish](https://kapravelos.com/publications/crawlphish-sp21.pdf)). PHOCA mendeteksi kit reverse-proxy MITM dari timing jaringan dan TLS dengan akurasi **99,9%**. Dari 1.220 situs MITM yang ditemukan, hanya 43,7% domainnya ada di blocklist ([Kondracki et al., CCS 2021](https://par.nsf.gov/servlets/purl/10337720)). Fitur trafik TLS terenkripsi mencapai ~95% di dataset lab ([Kumar et al., Cluster Computing 2023](https://doi.org/10.1007/s10586-023-04042-6)). Semua angka ini berasal dari crawler, sandbox, atau sensor jaringan yang tidak bisa dijalankan Shoo di iPhone. Catatan riset tidak menemukan satu pun studi peer-reviewed yang mengukur akurasi, FPR, atau latensi hook ekstensi atau Resource Timing dari pengguna nyata.

Bukti yang paling bisa dipindahkan ke Shoo justru datang dari DOM dan klaim merek. Reuse kit sangat tinggi: sepuluh keluarga kit Belanda teridentifikasi di **1.363 domain** ([Bijmans et al., USENIX Security 2021](https://www.usenix.org/conference/usenixsecurity21/presentation/bijmans)). Analisis 1.300 kit menyebut komponen halaman "very similar or even identical across kits" ([Ousat et al., arXiv 2608.07451](https://arxiv.org/abs/2608.07451)). Untuk pasangan merek-vs-domain, recall Phishpedia naik dari 40,16% ke 72,80% saat basis merek diperluas, dan ke 86,90% saat merek juga diekstrak dari teks HTML ([KnowPhish, USENIX Security 2024](https://arxiv.org/html/2403.02253v2)). Menambahkan perbandingan merek-vs-domain yang deterministik menaikkan recall Claude dari ~65% ke ~92% ([Lee et al., eCrime 2024](https://arxiv.org/html/2408.05941v1)). Gerbang credential-requiring page memangkas false positive **86,5%** ([PhishIntention, USENIX Security 2022](https://www.usenix.org/conference/usenixsecurity22/presentation/liu-ruofan)). Fitur SFH (form handler kosong atau `about:blank`) tergolong fitur "abnormal-based" yang "universally applicable" lintas dataset ([arXiv 1903.05675](https://arxiv.org/pdf/1903.05675)). Satu peringatan berlaku untuk semuanya: FP detektor sidik jari kit pada trafik benign nyata belum pernah diukur.

|---|---|---|---|

| Sidik jari struktur kit (nama/id field, kerangka DOM) | Bijmans, Nahapetyan (FMI 0,98), Ousat | Klasterisasi crawler | Sedang (FP belum diukur) |

## Kasus helpnets.info: semua bukti sudah ada di snapshot

Analisis lokal 26 Okt 2026 (curl tanpa JS, lalu kode layer 1–3 Shoo dijalankan atas PageSnapshot buatan) menunjukkan pola kegagalan yang jelas. Klaim merek ada, tetapi tersaring oleh pengecualian yang dirancang untuk mencegah false positive. URL `https://helpnets.info/0442827f6o7cfb43933ba59e2881cc906b7c.html/` mengembalikan HTTP 200 tanpa redirect, dengan `server: cloudflare` dan `x-amz-expiration … rule-id="DeleteAfter30Days"` (S3 di belakang Cloudflare). Menurut RDAP, domain itu didaftarkan 2018-02-12. Layer 1 dan 2 memberi 0, karena domain tidak memuat nama merek. Layer 3 hanya memicu `asks_password` (15). `brand_logo_offsite` diam karena `ALT_EXEMPT` di `ai/src/layer3/content.js` sengaja mengabaikan alt "Microsoft" agar tombol "Sign in with Microsoft" tidak memicu sinyal, dan judul "Sign in to your account" tidak menyebut merek. Total 15 berada di bawah ambang warning 30. Layer 4 lolos gerbang (skor ≥ 15), tetapi `buildInput` di `ai/src/layer4/reality.js` hanya mengirim host, judul, label field, dan ID aturan, sehingga kata "Microsoft" tidak pernah sampai ke LLM.

Sinyal jaringan tidak akan menyelamatkan kasus ini. Tidak ada redirect yang bisa dihitung. Cloudflare sebagai NS dan proxy adalah sinyal netral. Domainnya berumur delapan tahun. Header `x-amz-expiration` dengan aturan 30 hari menarik sebagai petunjuk hosting sekali pakai, tetapi belum ada bukti untuk fitur ini, dan header dokumen utama tidak bisa dibaca dari ekstensi iOS. Satu-satunya jalan untuk membacanya adalah request ulang, dengan semua risiko yang sudah dibahas. Resource Timing hanya akan menunjukkan bahwa semua aset datang dari `lp.cybeready.net`, dan fakta yang sama sudah terbaca dari atribut `src` di DOM. Sebaliknya, DOM-nya sangat khas. Ada `<meta name="PageID" content="ConvergedSignIn">`, field `loginfmt` (id `i0116`), `passwd` duplikat tersembunyi (id `i0118`, class `moveOffScreen`), dan tombol `idSIButton9`. Menurut analisis kasus, nama dan ID ini persis milik halaman login Microsoft asli. Favicon dan logo bernama `microsoft_favicon_a.ico` dan `microsoft_logo.svg`, dimuat dari domain yang bukan milik Microsoft.

Temuan terpenting dari pembacaan kode: **sidik jari kit sudah ada di data yang dikirim hari ini**. `snapshot.js` mengambil `input, select, textarea` beserta `name` dan `id`, termasuk `<input type="submit">`. Jadi `loginfmt`, `i0116`, `i0118`, `passwd`, dan `idSIButton9` semuanya ada di `forms[].fields`. Alt "Microsoft" juga ada di `imageAlts`. Aturan sidik jari Microsoft karena itu tidak membutuhkan perubahan PageSnapshot. Yang dibutuhkan hanya ID sinyal baru, dan menurut `contracts/detector-interface.md` itu tetap merupakan perubahan kontrak. Meta `PageID`, `src` favicon/logo, dan class `logo` belum dikumpulkan, jadi ketiganya butuh perubahan snapshot.

Kandidat perbaikan berbeda jauh dalam risiko false positive. Pengecualian `ALT_EXEMPT` ada karena alasan yang sah. Halaman login SaaS sering menampilkan field password sendiri bersama tombol SSO berlogo Microsoft, jadi "alt Microsoft + field password" saja akan menembak halaman legit. Syarat class `logo` membantu, tetapi butuh perubahan snapshot dan mudah dihindari kit. Sinyal yang jauh lebih tajam adalah favicon. Tombol SSO tidak pernah mengganti favicon halaman, sehingga favicon bernama merek dari host bukan-merek adalah klaim identitas halaman, bukan dekorasi. Inferensi ini belum diukur, tetapi sejalan dengan pemakaian favicon dalam pemantauan merek ([Google Threat Intelligence](https://gtidocs.virustotal.com/docs/use-cases-phishing-brand-monitoring)). Untuk empat merek di `ALT_EXEMPT`, aturan yang aman adalah meminta **dua sumber merek independen**, misalnya alt + nama file favicon, atau alt + sidik jari kit. Action form kosong dengan field password (SFH) murah dan sudah dikumpulkan, tetapi banyak form login SPA yang sah juga tidak punya action, jadi bobotnya harus kecil. Field password duplikat yang digeser keluar layar juga disalin dari halaman asli, sehingga nilainya sudah tercakup oleh sidik jari kit. Sinyal "tidak ada aset dari domain merek" lemah sendirian, karena kit bisa meng-host aset sendiri atau justru me-hotlink aset merek. Sinyal ini baru berarti setelah ada daftar CDN resmi per merek.

Simulasi skor di bawah memakai bobot usulan yang belum dikalibrasi. Bobot dimiliki Team AI (kini lead), ambang dimiliki lead: 30–79 warning, ≥ 80 blocked.

| Langkah | Sinyal | Bobot usulan | Skor kumulatif | Status |
|---|---|---|---|---|
| Sekarang | `asks_password` | 15 | 15 | normal |
| + sidik jari kit Microsoft (data sudah ada) | `brand_kit_clone` (ID baru) | 40 | 55 | warning |
| + klaim merek favicon/logo (dua sumber) | `brand_logo_offsite` (bobot penuh karena `asksData`) | 25 | 80 | blocked |
| + SFH action kosong + password | ID baru atau digabung ke form signal | 10 | 90 | blocked |
| + layer 4 dengan petunjuk merek | `unreasonable_request` | 30 | 100 | blocked |

Halaman ini kemungkinan halaman latihan CybeReady, vendor simulasi phishing. Menandainya tetap benar, karena polanya identik dengan kit sungguhan. Allowlist vendor simulasi tidak disarankan, karena host latihan berganti-ganti dan bisa ditiru penyerang.

## Kesimpulan

Keterbatasan jaringan iOS ternyata hampir tidak berpengaruh pada kasus yang lolos. Celah Shoo bukan di data yang tidak bisa dilihat, tetapi di data yang sudah dipegang dan belum dipakai: ID field kit, alt merek yang disaring terlalu luas, dan petunjuk merek yang tidak diteruskan ke layer 4. Satu pelajaran desain menonjol. Pengecualian anti-false-positive yang dibuat dengan alasan baik (`ALT_EXEMPT`) menciptakan titik buta yang presisinya justru tinggi: kit yang meniru merek SSO besar. Pengecualian semacam itu sebaiknya mensyaratkan bukti kedua, bukan membuang sinyal. Kalau sinyal runtime ditambahkan, nilai terbesarnya ada pada kit yang mengirim kredensial langsung ke Telegram atau Discord dari browser. Hook seperti itu hanya boleh menaikkan skor, dan keberhasilannya harus diukur dengan set uji Shoo sendiri, karena literatur belum punya angkanya.

Pertanyaan privasi juga perlu diangkat ke lead. Kontrak `/analyze` sudah mengirim seluruh PageSnapshot (URL, teks 20 ribu karakter, form) ke server tanpa disimpan. Artinya, aturan "server hanya menerima registrable domain" sudah punya pengecualian de facto untuk layer 3. Fitur baru di laporan ini dirancang agar dihitung di perangkat dan hanya mengirim ID turunan (misalnya ID merek dan boolean). Dengan begitu fitur baru tidak memperlebar pengecualian itu, dan status pengecualian tersebut tetap perlu diputuskan secara eksplisit di issue.

## Wajib diuji di iPhone asli

Simulator iOS 18.4 bermasalah untuk Safari Web Extension, dan engineer Apple menyarankan perangkat fisik ([Apple Developer Forums 785440](https://developer.apple.com/forums/thread/785440)). Uji di iOS 18.x dan 26.x, termasuk satu perangkat ber-RAM rendah.

| # | Yang diuji | Cara cek |
|---|---|---|
| 1 | Halaman uji lokal yang meniru ID field Microsoft (bukan URL hidup) memicu sinyal sidik jari, dan latensi `analyzeLocal` tetap < 50 ms | Halaman lokal dengan `loginfmt`/`i0116`/`i0118`/`idSIButton9`; ukur `performance.now()` |
| 2 | Sidik jari tidak menembak di halaman Microsoft asli dan halaman SSO | `login.microsoftonline.com`, `login.live.com`, tenant Entra ber-branding, halaman SaaS dengan "Sign in with Microsoft" |
| 3 | `link[rel~=icon]` terbaca, termasuk saat halaman tidak mendeklarasikannya (default `/favicon.ico`) | Log hasil di content script |
| 4 | `typeof browser.webRequest` dan apakah `onHeadersReceived`/`onBeforeRedirect` terpicu untuk `main_frame` | Listener + log pada situs dengan 301/302 |
| 5 | `registerContentScripts({world:'MAIN', runAt:'document_start'})` berjalan sebelum `fetch` inline di `<head>` | Halaman uji dengan `fetch` inline; cek apakah tertangkap |
| 6 | Pengaruh CSP halaman pada script MAIN world terdaftar | Halaman uji dengan CSP ketat |
| 7 | `allFrames` + `match_about_blank` menyuntik iframe `about:blank` yang dibuat script (celah bypass hook) | Halaman uji yang mengambil `fetch` dari `iframe.contentWindow` |
| 8 | Pemuatan pertama setelah izin diberikan mengikuti `run_at` atau tidak | Log urutan injeksi pada situs baru |
| 9 | `performance.getEntriesByType('resource')` dari ISOLATED world mengembalikan entri halaman; `initiatorType` untuk `sendBeacon`/`fetch` | Bandingkan dengan MAIN world |
| 10 | Refetch background lintas origin setelah `permissions.request`: apakah `r.headers.get('server')` terbaca; User-Agent, cookie/ITP, iCloud Private Relay | Fetch ke host tanpa `Access-Control-Allow-Origin` |
| 11 | Hook MAIN world tidak merusak situs bank dan SDK anti-fraud yang memeriksa `toString` | Uji pada situs bank/e-wallet Indonesia |
| 12 | Hanya jika URL Filter dikejar: cakupan subresource, koeksistensi dengan filter lain, bypass dari WhatsApp | Build development-signed (bebas entitlement) |
